## 这是什么

一个**演示用的总项目**。它自己不产出业务内容，它管着 `projects/` 下四个不同类型的子项目：
一个代码项目、一个实验项目、一个文档仓库，以及一个自己又往下嵌了一层的父项目。

四个子项目彼此**没有业务关联**——这是刻意的。它们各自演示一种项目类型该怎么干活，
合在一起演示的是**同一套骨架能装下四种性质完全不同的工作**。

### 🔴 为什么是「父子树」这种形状

**目录树就是任务拆解树。** 一个大需求必然拆成小任务，小任务还能再拆，
子项目自己又能当父项目——层数没有上限。调研与实验会不断催生「这条路值得单独试一下」的方向，
每个值得试的方向就在树上开一个子项目去试。

🔴 **尝试可以死，档案必须留。** 放弃的方向是**资产不是垃圾**——它至少证明了这条路不通。
所以放弃的子项目不删目录、不移出树，只改状态并写清放弃说明（见下「子项目的退场」）。

这么做的目的只有一句：**让所有相关的尝试都长在同一棵树上**，各有来由、各有结局，
而不是变成一堆互不相干、来由不明的文件夹散落在各处。

## 核心设计原则：对 AI agent 友好

| 原则 | 落地方式 |
|---|---|
| README 是写给 agent 的**接口**，不是宣传页 | 开头两三段自我介绍 + 完整索引表。agent 靠它决定读哪个文件，而不是把整棵树读一遍 |
| 规矩靠**钩子机器拦截**，不靠文字呼吁 | 三个钩子：`.githooks/pre-commit` 提交硬闸 · `boundary-guard.sh` 越界拦截 · `harness-check.sh` 确立仪式 |
| 状态用**标记文件**表达，不靠会话记忆 | `.claude/HARNESS-STATUS.md`（确立状态）· `.claude/cross-edit-allow`（临时授权） |
| 路径一律**相对** | 全仓库不出现绝对路径，换机器 / 改目录名照常工作 |
| 局限**如实写出来** | 每个钩子在自己的注释里写明「我拦不住什么」，不假装铁桶 |

## 父项目范式

**父项目的交付物是「秩序」，不是代码。** 它自己几乎不产出业务内容，它的活是：

| 该做 | 不该做 |
|---|---|
| 维护 `README.md` 的子项目索引表 | 替子项目写代码 |
| 写统筹文档（分工 / 依赖 / 优先级） | 把子项目的日志抄到父日志里 |
| 新建 / 归档子项目 | 在父项目根目录堆业务文件 |
| 维护本项目自己的规矩与钩子 | 跨到子项目树里改东西（见 [`.claude/rules/boundary.md`](.claude/rules/boundary.md)） |

### 🔴 git：独立嵌套仓库

- `projects/` 整个被父仓库 `.gitignore` 排除。
- **每个子项目自己 `git init`，是一个完整独立的仓库。**
- 每个仓库各自执行一次：`git config core.hooksPath .githooks`

不用 submodule / subtree 的理由：submodule 要在父仓库存子仓库的 commit 指针，
子项目每提交一次就得回父仓库更新一次指针——这与「父级日志只记父级」直接冲突，
且极易忘、忘了就是脏状态；subtree 则把历史搅在一起，子项目没法独立迁走。

后果（必须知道）：**在父仓库 `git status` 里看不到任何子项目的改动。**
子项目的事在子项目里提交。父项目只在自己的日志里记「新增/归档了哪个子项目」。

## 干活纪律

### 提交

```
git add <显式路径>     # 🔴 不用 git add -A / git add .
git commit
```

不用 `-A` 的理由：`-A` 会把你没打算提交的东西一起卷进来，
而本项目每次提交都要在 CHANGE-LOG 里对应一条记录——**卷进来的东西没法写进那条记录**。

提交前 `.githooks/pre-commit` 会强制两件事（见 [`.claude/rules/docs-discipline.md`](.claude/rules/docs-discipline.md)）：

1. 改了任何东西 → `CHANGE-LOG.md` 必须一起暂存，
   且必须**真的新增一行记录**（🔴 把本次说明改写进上一条记录那一行不算，闸门会拒）
2. `docs/` 或 `projects/` 有新增/删除/改名 → `README.md` 必须一起暂存

### 边界

**只写本项目树内的文件。** 越界由 `.claude/hooks/boundary-guard.sh` 拦截。
真要跨界走授权流程：[`.claude/rules/boundary.md`](.claude/rules/boundary.md) §3（口头同意 → 写放行条 → 改 → 提醒对方补日志 → 删放行条）。

🔴 **改 `projects/` 下的子项目也算越界**——它们是独立仓库、有自己的宪法和提交硬闸。
**但钩子拦不住这个方向**：子项目物理上就在本项目树内，`boundary-guard.sh` 按「是否在树内」判定，
所以在这里改子项目**机器上是放行的**。正因为没有机器兜底，这条更要自己守住——
**要改就去那个子项目的目录里开会话。**

### 🔴 在父项目会话里跨子项目干活：几个仓库，几次提交

一次会话里同时改了父项目和若干子项目（**不推荐**，但确实会发生）时，**提交不是一次，是几次**：

| 改动落在哪 | 在哪提交 | 谁把关 |
|---|---|---|
| 某个子项目的文件 | 到那个子项目目录里提交（`git -C projects/<名> ...` 或 `cd` 过去，都行） | 那个子项目自己的 `pre-commit`：要**它自己的** `CHANGE-LOG.md` 净增一条记录 |
| 父项目自己的文件（索引表 / 统筹文档 / 父日志） | 父项目根 | 父项目的 `pre-commit` |

钩子按仓库各自加载、各自生效，互不干扰；一次会话把几个仓库的提交都代办掉是允许的。
🔴 **但绝不能把子项目的改动提进父仓库**——`projects/` 被 `.gitignore` 排除是故意的：
不排除的话内嵌仓库会被父仓库记成一个 commit 指针（gitlink），子项目每提交一次、父仓库就得跟着更新一次指针。

🔴 **项目主人明确要求这么干的时候就照办**：按上面这张表把每个仓库各提交一次，
不要拿「边界」那一条一口回绝、也不要停下来反复要授权——他要的是活干完并且提交落对地方，不是一次拒绝。

🔴 **最容易漏的一步：父根的 `git status` 永远是干净的**，它看不见任何子项目的脏改动。
跨子项目干完活，**别拿父根的 `git status` 当「全都提交完了」的凭据**——它答的只是父仓库自己。
逐个仓库查（`git -C projects/<名> status --short`），或者在树根跑一次全树扫描：

```bash
find . -type d -name .git -not -path "*/.git/*" | while read g; do d=$(dirname "$g"); [ -n "$(git -C "$d" status --porcelain)" ] && echo "🔴 $d 有未提交改动"; done
```

没有任何输出 = 这棵树上所有仓库都干净。

⚠️ 还要知道：这样的会话**没跑过子项目的确立检查**，子项目的宪法也只在真的碰到它目录里的文件时才被带进上下文——
等于**拿父项目的规矩改子项目**。所以口径不变：**正式开发去子项目目录单开会话**；
这一节只管另一件事——**已经在父会话里改了，怎么把提交做对。**

### 新建子项目：七步，最后一步最容易忘

1. 判断类型——判据是**交付物长什么样**：
   能跑的东西 → 代码项目；一个结论 → 实验项目；要反复翻的知识 → 文档仓库；管着一堆产出内容的 → 父项目
2. 找**复制源**，复制到 `projects/` 下并改名。按这个顺序找：
   ① 本项目 `projects/` 下同类型的现有子项目（首选，它已经贴合本项目的规矩）；
   ② 本项目里还没有同类型的 → 去**当初建本项目所用的那份模具**取对应类型的样板。
   🔴 模具在哪，写在本项目 `CHANGE-LOG.md` **最早那条立项记录**里；那里也没写就去问项目主人。
   **不要凭猜去找，更不要从零手搓一套骨架**——手搓的骨架一定漏钩子，而漏了钩子不会报错。
3. 清掉示例内容，**保留骨架与格式示范**
4. 删 `.git/`，重新 `git init -b main`
5. `git config core.hooksPath .githooks`
6. 改写子项目的 `README.md` / `CHANGE-LOG.md`；**不改它的 `.claude/HARNESS-STATUS.md`**（留给确立仪式）
7. 🔴 **回到父项目**：`README.md` 索引表加一行（含**状态**列，新建时填 🚧 进行中）
   + `CHANGE-LOG.md` 记一条 + 在父项目提交。
   🔴 **那条记录必须写明来由**：这个子项目因哪个需求 / 哪份调研 / 哪条实验结论而建（一句话就够）。
   来由是判断「它还该不该活着」的唯一依据——不写，半年后没人知道这个目录为什么存在。

⚠️ 第 7 步**没有钩子兜底**：`pre-commit` 规则二本来管「`projects/` 下有新增就要求同步 README」，
但 `projects/` 被 `.gitignore` 排除，git 看不到那次新增，**规则二不会触发**。这一步靠纪律。

**暂时没有脚本，不要自己造一个**——现阶段项目数量少，手工做一遍能让人真正记住机制。

### 子项目的退场：放弃 ≠ 删除

🔴 **放弃一个子项目，不删目录、不移出 `projects/`、不清它的历史。**
「决定不做」本身是信息——它至少证明了这条路不通；删掉就等于这次尝试没发生过，
下一个人（或者半年后的你自己）会把同一条死路重走一遍。

两步走，各自按提交纪律留痕：

| # | 做什么 | 在哪提交 |
|---|---|---|
| 1 | `README.md` 索引表里这一行的状态改成 🗄 已放弃（留档） | 父项目，记一条父级 CHANGE-LOG |
| 2 | 子项目 `README.md` **顶部**加「放弃说明」：为什么停 / 验证到哪 / 若重启从哪接 | 子项目自己，记它自己的一条 CHANGE-LOG |

状态列只有四个取值：**🚧 进行中 · ⏸ 暂停 · ✅ 已完成 · 🗄 已放弃（留档）**。
它答的是**生命周期**（这个节点还活着吗），不是「能不能跑」——运行情况写进「是什么」列。

## 保持工作区真实

- 不把未验证的写成已完成；不隐藏失败的测试。
- 做完了就干脆说做完了；跳过了就说跳过了并说明原因。
- **看板/状态文件没写的事等于没发生过**——状态变化当场写盘，不攒到最后。
