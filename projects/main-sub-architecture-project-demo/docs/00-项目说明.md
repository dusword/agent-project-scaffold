# 00 · 项目说明：这组子项目为什么这么摆

> 父项目的统筹文档。回答三件事：**这里在管什么 / 为什么拆成这几个 / 父项目自己的边界在哪。**
> 具体规矩见项目根 [`CLAUDE.md`](../CLAUDE.md)；子项目各自的说明在它们自己的 `README.md`。

---

## 1. 在管什么

四个子项目，**类型各不相同，彼此没有业务关联**：

| 子项目 | 类型 | 在做的事 |
|---|---|---|
| `demo-code-project` | 代码项目 | 一个命令行单位换算器（长度 / 重量 / 温度） |
| `demo-experiment-project` | 实验项目 | 验证缓存淘汰策略选 LRU 还是 LFU |
| `demo-docs-project` | 文档仓库 | 沉淀业务规则与调研笔记 |
| `demo-parent-project` | 父项目 | 统筹「把散落的定时任务收拢」这一组工作，自己下面又挂着子项目 |

**它们凑在一起的唯一理由**：合起来能演示「同一套骨架装得下四种性质完全不同的工作」。
真实项目里，一个父项目下面的子项目通常是围绕同一个业务目标的——比如 `demo-parent-project` 就是那样。

---

## 2. 🔴 为什么按「类型」拆，不按「主题」拆

**类型不同则纪律不同。** 硬塞在一个项目里，两套纪律会互相打架，最后哪套都不执行：

| 类型 | 它的核心纪律 | 塞在一起会怎样 |
|---|---|---|
| 代码项目 | **测试是提交准入**，没有测试的功能不成立 | 实验脚本天天在改、天天没测试，这条会被当成噪音关掉 |
| 实验项目 | `EXPERIMENTS.md` **只增不改**，写过的轮次不许回头修 | 代码重构时顺手「订正」了旧轮次的数字，实验记录就成了废纸 |
| 文档仓库 | 新材料**先进 `inbox/`**，每份标来源 / 日期 / 可信度 | 混进代码仓库后，文档变成「顺手写的说明」，没人标可信度 |
| 父项目 | 交付物是秩序，**根目录不堆业务文件** | 一旦开始在父项目里写业务代码，索引和统筹就没人维护了 |

判断该建哪一类，用一句话：**你最终要交付的那个东西，长什么样？**

| 你会这么说 | 那就是 |
|---|---|
| 「做完之后**有个东西能运行**」 | 代码项目 |
| 「做完之后**知道该选哪条路**」 | 实验项目 |
| 「做完之后**有份东西以后要一直翻**」 | 文档仓库 |
| 「它自己不产出内容，**它管着一堆产出内容的**」 | 父项目 |

判不准也不致命——四类骨架是同一套，改的只是 `CLAUDE.md` 里的范式段落。

---

## 3. 依赖与顺序

**这四个子项目之间没有依赖，可以任意顺序推进。** 这是刻意的：
本项目要演示的是结构，不是工期编排。真实项目里若存在依赖（比如「实验出结论 → 才好动手写代码」），
应当在本文档里画清楚，并在索引表的「状态」列体现。

`demo-parent-project` 内部**有**一条真实的依赖示范，见它自己的 `docs/00-统筹说明.md`。

---

## 4. 父项目自己的边界

| 归父项目 | 不归父项目 |
|---|---|
| 维护 `README.md` 的子项目索引表 | 子项目里的任何代码 / 文档 / 实验 |
| 写本文这类统筹文档 | 子项目的 CHANGE-LOG |
| 维护共用的规矩（`.claude/rules/`）与三个钩子 | 子项目对规矩的本地化调整（那是它们确立仪式里的事） |
| 新建 / 归档子项目 | 替子项目做技术选型 |

🔴 **改 `projects/` 下的东西 = 越界。** 它们是独立仓库、有自己的宪法和提交硬闸。

⚠️ **但这个方向没有机器兜底**：子项目物理上就在本项目树**内**（`projects/<子项目>/`），
而 `boundary-guard.sh` 按「目标是否在本项目树内」判定，所以在这里改子项目**它一律放行**。
（详见 [`../.claude/rules/boundary.md`](../.claude/rules/boundary.md) §4 局限表。）

**正因为没有机器兜底，这条更要自己守住**——要改就去那个子项目的目录里开会话改。
兜底只剩两道，都是事后的：子项目自己的 `pre-commit` 会要求你补它的 CHANGE-LOG；
以及子项目独立的 git 历史让这次改动**事后可审计**（谁在哪次提交里动了什么，一查便知）。
真要跨界，走 [`../.claude/rules/boundary.md`](../.claude/rules/boundary.md) §3 的四步授权。

---

## 5. 什么时候该拆一个新子项目

出现下面任一情况，就该拆，而不是往现有项目里塞：

| 信号 | 说明 |
|---|---|
| **交付物形态变了** | 本来在写代码，现在要出一份「选哪个方案」的结论 → 拆实验项目 |
| **纪律开始打架** | 「这部分不用写测试吧」这句话反复出现 → 说明塞进来的东西不属于这个类型 |
| **有人要单独把它拿走** | 需要独立迁移 / 归档 / 交给别人 → 它本来就该是独立仓库 |
| **README 索引表说不清了** | 一行说明写不完一个目录在干什么，通常是它承担了两件事 |

反过来，**不该拆**的信号：只是文件多了、只是目录深了。
那是整理目录的事，不是拆项目的事——**每个子项目都有固定成本**（一套 harness、一份 README、一条历史）。

值不值这个成本，用三条判据量一下，**占两条就该拆**：

| # | 判据 | 换句话说 |
|---|---|---|
| 1 | 它有**自己的交付物**和自己的生命周期 | 它能独立地「做完」，也能独立地「做不完」 |
| 2 | 它**可能被单独放弃** | 放弃它，父项目照样能往下走 |
| 3 | 它需要**独立的档案和历史** | 以后要单独翻它做过什么、为什么这么选 |

一条都不占、只是父项目的一个章节或一份文档 → 写进父项目的 `docs/`，不开新仓库。

### 拆出来之后：来由和结局都要留

| 时点 | 该留下什么 |
|---|---|
| 拆的时候 | 父项目 CHANGE-LOG 那条记录写明**来由**（因哪个需求 / 哪份调研 / 哪条实验结论而建）；README 索引表加一行，状态填 🚧 进行中 |
| 做完了 | 状态改 ✅ 已完成 |
| 有意搁置 | 状态改 ⏸ 暂停 |
| 做不下去了 | 状态改 🗄 已放弃（留档），**目录不删**，子项目 README 顶部写「放弃说明」 |

🔴 **实验 / 文档类子项目「导出的新方向」被采纳时，标准动作就是按七步再开一个新子项目**，
来由指回那份调研或那条实验结论。这样树上每个节点都能往前查到「因什么而生」、
往后查到「怎么结束的」——**这就是为什么相关的尝试要长在同一棵树上，而不是散落各处。**

新建步骤见项目根 [`CLAUDE.md`](../CLAUDE.md)「新建子项目：七步」；退场步骤见同一份文件的「子项目的退场」。
🔴 第 7 步（回父项目更新索引 + 记日志）**没有钩子兜底**，因为 `projects/` 被 `.gitignore` 排除，
git 看不到那次新增。**靠纪律，别忘。**
