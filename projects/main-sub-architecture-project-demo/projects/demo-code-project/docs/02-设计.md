# 02 · 设计

> 示范「代码项目」的设计文档：**两段说清架构，不写成源码的复述。**
> 判据：这份文档要回答的是「为什么这么分」，不是「每个函数干什么」——后者看源码更准。

## 1. 三层单向依赖

```
cli.py         交互层   解析参数 · 翻译错误 · 决定退出码     ← 唯一碰 IO 的地方
   ↓
converter.py   逻辑层   纯函数：输入数值出数值             ← 一行 print 都没有
   ↓
units.py       事实层   有哪些单位 · 换算系数是多少         ← 只有数据和查表
```

**依赖方向严格单向，反向引用一律禁止。**

这么分的三个理由：

1. **好测**。逻辑层是纯函数，测试不用起进程、不用捕获输出、不用管退出码。
   实际收益能量化：39 个测试跑完 0.03 秒，其中只有 10 个需要 `capsys` 捕获输出。
2. **好复用**。以后要加 HTTP 接口、或者让 AI agent 直接调用，
   接上 `converter.convert()` 就行，不用把 CLI 的参数解析逻辑抄一遍。
   （**人点命令行和机器调接口共用同一套实现**，不为两种用法写两份逻辑。）
3. **改动收敛**。新增一个长度单位，改动只落在 `units.py` 的一张字典里，
   另外两层一个字不用动。

### 为什么 `main()` 返回退出码而不是 `sys.exit()`

这样测试可以直接 `assert main(["1","km","m"]) == 0`，不用起子进程、不用抓 `SystemExit`。
真正的退出交给模块底部的 `raise SystemExit(main())` 和 `[project.scripts]` 入口。

**代价**：调用方必须记得处理返回值。这个代价可接受，因为调用方只有两处，且都在本项目里。

## 2. 温度为什么单独写

线性量纲（长度、重量）能用一张「相对基准单位的系数表」统一处理：

```
结果 = 数值 × 源系数 ÷ 目标系数
```

温度不行——它有**偏移量**（摄氏 0 度 = 华氏 32 度），是仿射变换而非线性变换。
硬塞进同一张表需要给每个单位加 `(系数, 偏移)` 二元组，
结果是**长度和重量的偏移永远是 0**，白白让 90% 的数据带上一个恒为零的字段。

所以选了：**线性量纲走查表，温度走 `_to_celsius` / `_from_celsius` 两个转换函数**。

| 方案 | 取舍 |
|---|---|
| 统一成 (系数, 偏移) 二元组 | 结构统一，但绝大多数数据带无意义字段；且以后遇到真正的非线性量纲（分贝、pH）照样塞不进去 |
| ✅ 线性查表 + 温度专用函数 | 多一个分支，但两种情况各自都最简单；将来加非线性量纲就是再加一个分支，不用重构已有的 |

**中转单位选摄氏**，不是开尔文——摄氏是三者里最常用的，
调试时打印中间值更容易一眼看出对不对。

## 3. 错误处理：抛到该抛的层

`converter` 层**只抛异常，不吞异常、不打印**：

- `UnknownUnitError`——单位不在任何表里
- `DimensionMismatchError`——两个单位量纲不同，带上 `source` / `target` 属性供上层组装消息

理由：这一层**不知道调用方是谁**。CLI 需要把它翻译成中文提示 + 退出码 1；
将来的 HTTP 接口需要翻译成 400 + JSON；agent 调用可能需要原样拿到异常类型做分支。
**在这一层决定「怎么告诉用户」，就等于替所有未来的调用方做了决定。**

`DimensionMismatchError` 特意保留 `source` / `target` 两个属性而不是只留一句消息，
就是为了让上层能重新组装措辞——测试 `test_量纲对不上时抛_DimensionMismatchError` 断言的正是这两个属性。
