> **类型：实验项目**（交付物 = 一个经过验证的结论，不是代码）。

## 在验证什么

某内部查询服务高峰期 P95 从 40ms 涨到 210ms，请求 key 分布高度集中 → 缓存应当有效。
但运维踩过坑：**每天凌晨的报表任务会全表扫描，加过缓存后「报表跑完接口反而更慢」**。

所以要先回答三个问题，再决定怎么加缓存：

| # | 问题 |
|---|---|
| V1 | 我们这种热点分布下，哪种淘汰策略命中率更高？ |
| V2 | 扫描型任务会不会把热点冲掉？冲掉多少？ |
| V3 | 需要多大容量才够？容量够大时策略选型还重不重要？ |

## 怎么跑

只用 Python 标准库，无第三方依赖。

```bash
# 第 1 轮：只跑稳态阶段，容量 64
python3 experiments/run_cache_bench.py --capacity 64 --phase steady

# 第 2 轮：全量轨迹（含扫描突发），容量扫描
python3 experiments/run_cache_bench.py --sweep 32,64,128,256
```

## 数据说明

`experiments/data/sample-requests.csv` 三列：`seq` / `phase` / `key`。

| 阶段 | 请求数 | 构成 |
|---|---:|---|
| `steady`（前段） | 1500 | 40 个热 key 占 70% 流量，160 个温 key 占 22%，1000 个冷 key 占 8% |
| `scan` | 500 | 全表扫描，每个 key **只出现一次**，之后再不出现 |
| `steady`（后段） | 500 | 同前段分布，用来看**扫描有没有把热点冲掉** |

🔴 后段那 500 次是整个设计的关键——只在扫描结尾停下是测不出损伤的。

🔴 **这是合成轨迹，不是生产采样**，分布参数是我们拍的。
这是本项目最大的不确定性来源，见 `docs/01-痛点与需求.md` §4。

## 当前状态

🟡 **两轮实验已完成，结论草案已成文，被 `docs/03-待决策.md` 的 Q1 挡住未定稿。**

| 结论 | 出处 |
|---|---|
| 加缓存有明确收益（命中率 60~70%） | 第 1 轮 |
| 稳态下 LFU 优于 LRU（+9.10pp） | 第 1 轮 |
| 🔴 容量越大策略选型越不重要（+10.24pp → +3.48pp） | 第 2 轮 |
| 扫描伤 LRU（-28 次命中）但 LFU 完全免疫（0 损失） | 第 2 轮 |
| ❌ 负面结论：「LFU 领先会随容量扩大」是错的 | 第 2 轮 |

**卡在哪**：LFU 的实现成本没评估（`docs/03-待决策.md` Q1），需要服务负责人拍板。
