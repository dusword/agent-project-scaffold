## 第 1 轮 · 稳态热点分布下，LRU 和 LFU 谁的命中率高

**日期**：2026-08-19

### 假设

服务的读请求是典型的热点分布（少数 key 承担大部分流量）。
在这种分布下，**LFU 应当优于 LRU**——因为 LFU 直接按访问次数排序，
而 LRU 只看「最近有没有被访问」，会被偶发的冷 key 挤掉热 key。

### 做法

- 轨迹：`experiments/data/sample-requests.csv` 的 `steady` 阶段，**2000 次请求 / 339 个唯一 key**
- 分布：40 个热 key 承担 70% 流量，160 个温 key 承担 22%，1000 个冷 key 承担 8%
- 容量：64（约等于唯一 key 数的 19%，刻意设成「装不下全部热+温」）
- 命令：

```bash
python3 experiments/run_cache_bench.py --capacity 64 --phase steady
```

### 数字

| 策略 | 容量 | 请求数 | 命中数 | 命中率 |
|---|---:|---:|---:|---:|
| LRU | 64 | 2000 | 1214 | **60.70%** |
| LFU | 64 | 2000 | 1396 | **69.80%** |

LFU 领先 **+9.10 个百分点**（相对提升 15.0%）。

### 判定

✅ **假设成立。** 稳态热点分布下 LFU 明显优于 LRU。

### 导出的新方向

1. 🔴 **稳态下赢 ≠ 生产环境能用**。真实系统里有报表任务、批量导出这类**扫描型突发**，
   一次性刷过大量只访问一次的 key。这正是 LRU 最容易被冲垮的场景，
   但 LFU 在这种场景下的表现**本轮没有测**。→ 第 2 轮。
2. 单一容量（64）的结论可能是巧合，需要做容量扫描确认趋势稳定。→ 并入第 2 轮。
3. 本轮只比了命中率，**没有比实现成本**。记进 `docs/03-待决策.md`。

## 第 2 轮 · 加入扫描突发后，两者各损失多少

**日期**：2026-08-19

### 假设

在稳态流量中插入一段**全表扫描**（500 个 key，每个只访问一次，之后再不出现）后：

- **LRU 会被显著冲垮**——扫描的 key 全是「最近访问过」的，会把热 key 挤出去
- **LFU 受影响较小**——扫描 key 的频次都是 1，会被优先淘汰

预期：LFU 的领先幅度**扩大**。

### 做法

- 轨迹：同一个文件的**全量** 2500 次请求 / 839 个唯一 key
  （1500 次稳态 → 500 次扫描 → 500 次稳态）
- 关键设计：扫描段之后**还有 500 次稳态请求**，这样才能看出「扫描有没有把热点冲掉」。
  只在扫描段结尾停下是测不出损伤的。
- 容量扫描：32 / 64 / 128 / 256，一并回答第 1 轮导出的方向 2
- 命令：

```bash
python3 experiments/run_cache_bench.py --sweep 32,64,128,256
```

### 数字

全量轨迹（2500 请求，其中 500 次扫描是**结构性不可能命中**的）：

| 容量 | LRU 命中率 | LFU 命中率 | LFU 领先 |
|---:|---:|---:|---:|
| 32 | 28.44% | 38.68% | +10.24pp |
| 64 | 47.44% | 55.84% | +8.40pp |
| 128 | 58.12% | 61.72% | +3.60pp |
| 256 | 61.60% | 65.08% | +3.48pp |

**关键对照**——把第 1 轮的命中数换算到同一分母（2500）再和本轮比，
就能剥离「500 次必然 miss」的机械影响，看出**扫描真正造成的损伤**：

| 策略（容量 64） | 第 1 轮命中数 | 本轮命中数 | 扫描造成的净损失 |
|---|---:|---:|---:|
| LRU | 1214 | 1186 | **-28 次命中** |
| LFU | 1396 | 1396 | **0 次命中** |

### 判定

✅ **假设成立，而且比预期更干净**：LFU 在本轨迹上对扫描突发是**完全免疫**的
（命中数一次不少），LRU 则被扫描吃掉 28 次命中。

❌ **但「领先幅度扩大」这半句错了**：容量越大，LFU 的领先反而**收窄**
（32 时 +10.24pp → 256 时 +3.48pp）。原因事后看很显然——容量大到能装下几乎所有热+温 key 时，
淘汰策略本身就不重要了，两者都接近上限。**这条是本轮最有价值的发现，因为它划出了适用边界。**

### 导出的新方向

1. **LFU 的已知代价本轮完全没测**：
   - 「老热点不退场」——一个曾经很热、现在没人用的 key，频次高，会一直赖在缓存里。
     本实验的轨迹是**平稳的**，热点从头到尾不变，**天然对 LFU 有利**。
     → 需要第 3 轮：造一段**热点漂移**的轨迹再比。
   - 时间衰减（TinyLFU / Window-TinyLFU）就是为这个问题存在的。
2. **实现成本没测**：本脚本的 LFU 是朴素实现，淘汰时用 `min()` 扫全表，是 **O(n)**。
   生产实现要上频次桶或最小堆。这是真实成本，登记进 `docs/03-待决策.md`。
3. 容量 ≥128 时两者差距 <4pp——**如果生产环境内存充裕，这个选型可能根本不值得纠结**。
   先去量一下生产实际的容量/唯一 key 比，再决定要不要做第 3 轮。

### 本轮的诚实边界

- 轨迹是**合成的**（`seed=20260819` 可复现），不是生产采样。分布参数是我们拍的，
  真实分布若明显不同，上面所有数字都要重跑。
- 只测了命中率，**没测延迟、内存开销、并发下的锁竞争**。
- 两种策略都是教学级实现，不代表工业实现的性能特征。
