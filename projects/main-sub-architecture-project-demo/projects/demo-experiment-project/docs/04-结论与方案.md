## 1. 已经站得住的结论

### C1 · 加缓存有明确收益，值得做

| 项 | 内容 |
|---|---|
| **依据** | 第 1 轮：容量 64（约唯一 key 数的 19%）时，命中率 60.70%（LRU）~ 69.80%（LFU） |
| **含义** | 后端存储的读压力可以降到原来的 3~4 成 |
| **边界** | 基于合成轨迹（`seed=20260819`）。若生产分布明显不同，这个数字要重跑 |

### C2 · 在稳态热点分布下，LFU 的命中率优于 LRU

| 项 | 内容 |
|---|---|
| **依据** | 第 1 轮：LFU 69.80% vs LRU 60.70%，**+9.10pp**（相对提升 15.0%） |
| **边界** | 仅在容量 = 64 这一个点上测的；容量趋势见 C3 |

### C3 · 🔴 容量越大，策略选型越不重要

| 项 | 内容 |
|---|---|
| **依据** | 第 2 轮容量扫描：LFU 的领先从容量 32 时的 +10.24pp，单调收窄到容量 256 时的 +3.48pp |
| **含义** | **如果生产内存充裕（容量能到唯一 key 数的 30% 以上），这个选型可能根本不值得纠结。** 与其花两周做策略优化，不如加内存 |
| **边界** | 只测了 4 个容量点；未测容量超过唯一 key 数时的情况（那时两者都趋近 100%，没有意义） |

### C4 · 扫描型任务确实会伤 LRU，但伤得比预想的轻

| 项 | 内容 |
|---|---|
| **依据** | 第 2 轮对照：插入 500 次扫描后，LRU 净损失 **28 次命中**，LFU 净损失 **0 次** |
| **含义** | 运维反馈的「报表跑完接口变慢」现象**方向属实**，但在本轨迹的量级下影响很小（28/1214 ≈ 2.3%）。若生产观测到的劣化远大于此，说明**还有别的原因**，不能全算在缓存头上 |
| **边界** | 扫描段只有 500 个 key。生产的报表任务可能扫过全部数据，量级差很多——**这条结论对扫描规模敏感** |

## 2. 尚不能下的结论

| 问题 | 为什么还不能下 |
|---|---|
| **到底选哪个策略** | 被 Q1 挡住：LFU 的实现成本还没评估。命中率高不等于该选它 |
| **热点漂移时 LFU 会不会退化** | 完全没测。见 Q2。这是 **LFU 的经典缺陷**，我们的轨迹恰好回避了它 |
| **需要多大内存** | C3 给了趋势，但没有生产的「唯一 key 数」这个基数，换算不出绝对值 |

## 3. 建议的下一步（按优先级）

| # | 动作 | 为什么排这个顺序 |
|---|---|---|
| 1 | **查生产的唯一 key 数与内存余量** | 如果内存充裕，C3 意味着整个策略选型可以直接跳过——这一步可能让后面几步全部作废，所以排第一 |
| 2 | **查生产 key 访问日志，看热点是否漂移**（Q2 选项 ②） | 事实问题，能查就别猜。查完才知道第 3 轮值不值得做 |
| 3 | **评估 Q1 的三个选项，服务负责人拍板** | 前两步的结果会直接改变推荐（内存充裕 → 选项 ③ 更有说服力） |
| 4 | 视情况做第 3 轮（热点漂移） | 只有第 2 步查出「热点确实漂移」才需要 |

🔴 **顺序不是随便排的**：第 1 步有可能让第 3、4 步整个不必要。
**先做那些「可能让后面的活作废」的事**，这是实验项目排期的通则。

## 4. 负面结论也记在这里

实验项目里，「这条路不通」和「这条路通」一样值钱。本项目目前的负面结论：

| # | 负面结论 | 出处 |
|---|---|---|
| N1 | **「LFU 的领先幅度会随容量扩大」——错的。** 实测是单调收窄 | 第 2 轮，假设的后半句被推翻（❌） |
| N2 | **「扫描会把 LRU 冲垮」——夸大了。** 实测净损失仅 2.3% | 第 2 轮对照表 |

N1 是本项目**最有价值的产出**——它划出了适用边界，
把「优化缓存策略」这件事从「必做」降级成了「先看内存够不够」。
