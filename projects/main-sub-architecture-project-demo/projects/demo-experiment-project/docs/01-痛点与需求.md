# 01 · 痛点与需求

> 实验项目的第一份文档：**先说清楚在痛什么，再说要验证什么。**
> 判据：如果这份文档删掉，别人能不能理解「为什么要做这些实验」？不能 → 没写够。

---

## 1. 痛点

某内部查询服务的读接口响应时间在业务高峰期明显变长。初步排查后确认：

| 现象 | 数据 |
|---|---|
| 高峰期 P95 延迟 | 从平峰的 40ms 涨到 210ms |
| 后端存储的 QPS | 高峰期是平峰的 3.2 倍 |
| 请求 key 的分布 | 目测高度集中——少数 key 占了大部分请求 |

**判断**：瓶颈在后端存储，而请求分布高度集中意味着**缓存应当很有效**。

### 但有一个已知的坑

服务每天凌晨跑一次报表任务，会**顺序扫过全部数据**。
运维反馈：「加过一次缓存，报表跑完之后接口反而更慢了一阵。」

这句话就是本项目存在的理由——**朴素地加个缓存可能适得其反**。

---

## 2. 要验证什么

| # | 问题 | 为什么非验证不可 |
|---|---|---|
| V1 | 在我们这种热点分布下，哪种淘汰策略命中率更高？ | 选错策略，缓存的收益直接砍掉一截 |
| V2 | 扫描型任务会不会把热点冲掉？冲掉多少？ | 这是运维已经踩过的坑，不能靠猜 |
| V3 | 需要多大容量才够？ | 容量决定成本；容量够大时策略选型可能根本不重要 |

🔴 **不验证的东西也要写清楚**（见 §4），否则后面的人会以为「实验做过了 = 全都验证过了」。

---

## 3. 交付物

**本项目的交付物是一个决策，不是一个缓存实现。**

具体是 `docs/04-结论与方案.md` 里的一句话建议 + 它的依据链：

```
建议 → 依据是第 N 轮实验的哪个数字 → 那轮实验的边界在哪
```

`experiments/` 下的脚本是**得出结论的工具**，不是交付物。
它们不需要做到生产质量，但**必须可复现**（固定随机种子、数据入库）。

---

## 4. 明确不验证的（本项目边界）

| 不做 | 理由 |
|---|---|
| 延迟 / 内存占用 / 并发锁竞争 | 需要真实压测环境，本项目只做离线轨迹回放 |
| 分布式缓存的一致性 | 单机缓存策略是前置问题，先把它定了 |
| 生产轨迹采样 | 拿生产数据要走审批；先用合成轨迹把结论的**形状**跑出来，形状对了再决定值不值得申请 |
| 具体缓存中间件选型（Redis / Caffeine / 自研） | 策略定了才谈实现载体 |

🔴 **合成轨迹是本项目最大的不确定性来源**，这一点在 `EXPERIMENTS.md` 每一轮的
「诚实边界」里都要重复写，不许省。

## 5. 预算

| 项 | 预算 | 现状 |
|---|---|---|
| 计算资源 | 本机跑，0 成本 | 实际每轮 <1 秒 |
| 付费接口 | **无** | —— |
| 人力 | 2~3 轮实验 | 已做 2 轮 |

🔴 **实验项目纪律：调付费接口或大规模跑数之前必须先报预算并等确认。**
本项目目前全部在本机用标准库跑，没有花钱环节；一旦要引入生产数据采样或云上压测，
**先回来更新这一节并得到确认**。
