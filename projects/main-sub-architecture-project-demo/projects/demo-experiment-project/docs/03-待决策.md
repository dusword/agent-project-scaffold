## Q1 · LFU 的实现成本能不能接受？

| 项 | 内容 |
|---|---|
| **状态** | 🟡 待决 |
| **背景** | 实验证明 LFU 命中率更高（第 1 轮 +9.10pp）且对扫描免疫（第 2 轮 0 损失）。但实验用的是**朴素实现**：淘汰时 `min()` 扫全表，是 **O(n)**。生产实现要么上频次桶（O(1) 但代码量约为 LRU 的 3 倍），要么上最小堆（O(log n)，还要处理频次更新时的堆调整）。而 LRU 在多数语言里有现成的、经过实战的实现（Python 的 `OrderedDict`、Java 的 `LinkedHashMap`） |
| **选项** | ① 上成熟的 W-TinyLFU 库（如 Caffeine），命中率与抗扫描都好，但引入一个新依赖；② 自己实现频次桶版 LFU，无新依赖但要自己维护正确性与并发安全；③ 就用 LRU + 给扫描任务单独走一条不经过缓存的路径，实现最简单，把问题从「策略」转成「流量隔离」 |
| **推荐** | **③**，理由是第 2 轮数字：容量 ≥128 时两者差距已收窄到 <4pp，而扫描的伤害（-28 次命中）本来就可以用流量隔离一次性消掉。用最简单的策略 + 一条 bypass，可能拿到 90% 的收益 |
| **谁来决** | 需要服务负责人拍板——这条涉及**是否引入新依赖**与**是否改报表任务的调用方式**，超出实验项目的权限 |
| **挡住了什么** | 挡住 `04-结论与方案.md` 定稿。目前结论只能写到「LFU 命中率更优」，写不到「所以就用 X」 |

## Q2 · 热点漂移场景要不要做第 3 轮？

| 项 | 内容 |
|---|---|
| **状态** | 🟡 待决 |
| **背景** | 第 2 轮的轨迹**热点从头到尾不变**，这对 LFU 天然有利——LFU 的经典缺陷正是「老热点不退场」：一个曾经很热、现在没人访问的 key，凭高频次赖在缓存里不走。我们的实验完全没有触及这个缺陷，**等于给 LFU 打了一场没有对手的比赛**。真实业务有没有热点漂移（比如商品下架、活动结束），目前**不知道** |
| **选项** | ① 直接做第 3 轮，造一段热点漂移轨迹（约半天）；② 先去查生产的 key 访问日志，确认热点到底漂不漂移，再决定要不要做（要等日志权限）；③ 不做，直接在结论里把这条写成「已知未验证风险」 |
| **推荐** | **②**。做第 3 轮的前提是「热点确实会漂移」，而这是个**事实问题**不是**实验问题**——能查就别猜。如果查下来热点很稳定，第 3 轮就是白做 |
| **谁来决** | 我们自己可以决，但需要有人给日志查询权限 |
| **挡住了什么** | 不挡任何事。`04-结论与方案.md` 可以先带着这条「已知未验证风险」定稿 |
