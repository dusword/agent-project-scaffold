# 文档纪律 · README 是接口，CHANGE-LOG 是历史

> 其中两条由 `.githooks/pre-commit` 机器强制。其余靠本文件约束。

---

## 1. 两份根文件的职责，别搞混

| 文件 | 回答什么问题 | 时态 | 谁读 |
|---|---|---|---|
| `README.md` | **现在**这个项目里有什么、怎么用 | 现在时 | 新来的人 / **新开会话的 AI agent** |
| `CHANGE-LOG.md` | **过去**发生过什么、为什么这么改 | 过去时 | 想搞清「这为什么长这样」的人 |

**判据**：一句话如果加上日期才成立 → 进 CHANGE-LOG；不加日期也成立 → 进 README。

---

## 2. 🔴 README 是写给 AI agent 看的接口

这是本体系最重要的一条设计原则。

新开一个会话的 agent，对项目一无所知，**它读到的第一份东西就是 README**。
所以 README 不是宣传页，是**接口文档**：

| 必须有 | 理由 |
|---|---|
| 一句话说清「这是什么、交付物是什么」 | agent 靠这句判断该用什么范式干活 |
| 🔴 一句「**为什么存在 / 源自哪里**」（来由） | 因哪个需求 / 哪份调研 / 哪条实验结论而建。缺了这句，半年后没人知道这个目录为什么在这儿 |
| **完整的内容索引表**（每个目录/文件一行 + 一句话说明） | agent 靠这张表决定去读哪个文件，而不是把整棵树读一遍 |
| 怎么起 / 怎么跑 / 怎么测（代码类项目） | agent 靠这个自验，不用猜 |
| 当前状态与已知缺口 | 防止 agent 把「没做」当成「做错了」去修 |
| 🔴 （父项目）子项目索引表带「**状态**」列 | 取值只有四个：🚧 进行中 · ⏸ 暂停 · ✅ 已完成 · 🗄 已放弃（留档）。它答的是**生命周期**（这个节点还活着吗），能不能跑这类运行情况写进「是什么」列 |

**反面写法**（都会让 agent 走弯路）：

- ❌ 「详见各目录下的说明」——agent 不知道该去哪，只能全读
- ❌ 索引表里有目录没有说明——等于没索引
- ❌ 写着「TODO：待补充」放了三个月——agent 会当真
- ❌ 索引表里子项目全标着「进行中」，其中一半半年没动过——**状态列失真等于没有状态列**

### 🔴 放弃的项目怎么在 README 里体现

**放弃 ≠ 删除。** 父项目把索引表里那一行的状态改成 🗄 已放弃（留档），**目录留在原位**；
被放弃的项目在自己 README 的**顶部**写一段「放弃说明」：

```markdown
> **🗄 放弃说明（YYYY-MM-DD）**
> **为什么停**：……
> **验证到哪**：已经确认了什么、还有什么没验
> **若重启从哪接**：下一个人接手该从哪个文件 / 哪一步开始
```

**「决定不做」本身是信息**——它至少证明了这条路不通。删掉档案等于这次尝试没发生过，
下一个人（或者半年后的你自己）会把同一条死路重走一遍。

### 机器强制的部分

`pre-commit` 规则二：暂存区里若有 `docs/` 或 `projects/` 下的**新增 / 删除 / 改名**，
`README.md` 必须一起暂存，否则拒绝提交。

只管结构变化、不管内容改动，是刻意的——**改一个错别字就逼你动 README 会制造噪音，
而目录多一个少一个不同步，索引就直接失真了。**

## 3. 🔴 CHANGE-LOG 是提交的准入条件

`pre-commit` 规则一：只要有任何非 `CHANGE-LOG.md` 的文件进暂存区，
**它所属那个项目单元**的 `CHANGE-LOG.md` 就必须一起进，否则拒绝提交。**没有跳过开关。**

**项目单元** = 从被改的文件所在目录往上找，最近的那个含 `CLAUDE.md` 的目录
（一路找到顶都没有，就算仓库根）。

在「一个项目 = 一个仓库」的标准形态下，整个仓库就是**一个**单元，本条与「动了就得留日志」
这个旧口径逐条等价，习惯一点不用改。差别只在一个仓库里并排装着多个项目时才看得出来：
一次提交**允许**同时动多个单元，但**每个被动到的单元都要各自补上自己的那行日志**——
谁也不能拿别人的日志顶包。

🔴 **光「在暂存区里」不算数**（规则一之二）：钩子还会看**该单元** `CHANGE-LOG.md` 的暂存 diff，
要求**记录行净增加至少一行**（记录行 = 首格是日期的表格行）。

**改旧行不算新增。** 把这次的说明写进上一条记录那一行，diff 上是一加一减、净增 0，
钩子会拒绝并告诉你「要另起一行」。这条是实测事故补上的：曾经有会话用 Edit 改日志时
把新内容揉进了上一条记录，闸门照常放行，最终 **5 次提交对 4 行记录**，全程零告警。

⚠️ 它只**数**记录行有没有多一条，**不判断**你写得对不对——内容质量仍然靠人工审阅。

### 格式

```markdown
| 日期 | 改了什么 | 为什么 |
|---|---|---|
| 2026-08-19 | 加了单位换算的温度模块 | 用户报的第一个需求缺口 |
```

新记录**加在表格最上方**（最新的在最前，读的人一眼看到近况）。

### 写法要求

| 要求 | 好例子 | 坏例子 |
|---|---|---|
| 写**为什么**，不只写做了什么 | 「拆出 units.py，因为换算表要被 CLI 和测试同时引用」 | 「重构」 |
| 一次提交一条 | 「加温度换算」 | 「加温度换算、修 README、调格式、顺手升级依赖」 |
| 用人话，不用 diff 语言 | 「换算失败时改为返回错误码而不是抛异常」 | 「修改 convert() 返回值类型」 |

### 🔴 日志条目 ↔ git 提交，一一对应

本体系的示范做法是：**一条 CHANGE-LOG 记录 = 一次 git 提交**。
所以提交前先写日志，日志写不出一句话来，说明这次改动没想清楚，或者攒太多该拆开。

`git log --oneline` 和 `CHANGE-LOG.md` 应该能对上号——这是判断一个仓库是否守纪律的最快方法。

## 4. 父级日志只记父级

**子项目的变化记在子项目自己的 CHANGE-LOG 里，不往上冒泡。**

父项目的 CHANGE-LOG 只记父级自己的事：

| 该记 | 不该记 |
|---|---|
| 新建了一个子项目 / 归档了一个子项目 | 某个子项目内部加了个函数 |
| 改了统筹文档 / 调整了子项目之间的分工 | 某个子项目修了个 bug |
| 改了父项目自己的规矩 | 某个子项目的依赖升级了 |

理由：父项目的 `projects/` 被 `.gitignore` 排除，子项目的改动**根本不在父仓库的提交范围内**。
硬要往父日志里记，写的是一份没有对应提交的假历史。

## 5. docs/ 的命名

| 约定 | 说明 |
|---|---|
| 数字前缀 | `00-` `01-` `02-`…… 表达**阅读顺序**，不是创建顺序 |
| `00-` 留给总纲 | 架构规范 / 统筹说明这类「先读这个」的文档 |
| 文件名用中文 | 除了编号前缀。中文名对人和 agent 都更直观 |
| 目录名用英文 kebab-case | `docs/` `experiments/` `mini-child-code-project/` |

编号一旦定下**不要重排**——别处引用会全部失效。要插在中间就用 `01b-`。
