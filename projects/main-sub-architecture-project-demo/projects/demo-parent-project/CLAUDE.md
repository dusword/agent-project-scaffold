# 项目宪法 · demo-parent-project

> **类型：父项目。交付物 = 秩序（分工 / 索引 / 规矩），不是内容。**
> 规矩细则在 [`.claude/rules/`](.claude/rules/)。冲突时：`.claude/rules/boundary.md` > 本文件 > 其它。

---

## 🔴 新会话第一件事

1. 读本文件
2. 读 [`README.md`](README.md) —— 子项目索引表
3. 读 [`docs/00-统筹说明.md`](docs/00-统筹说明.md) —— **这组项目在做什么、谁先谁后**
4. `git status --short` + `git log --oneline -5`

---

## 这是什么

一个父项目，`projects/` 下挂着子项目。同时是**「父项目」范式的可复制样板**，
并且**示范了递归**——它自己就在上一级总项目的 `projects/` 下，而它下面又挂着子项目。

```
docs/00-统筹说明.md              分工 / 依赖 / 顺序 / 父项目自己的边界
projects/mini-child-code-project 一个完整的孙项目（独立 git 仓库）
```

---

## 🔴 父项目范式

### 1. 父项目自己几乎不产出内容

| 该做 | 不该做 |
|---|---|
| 维护 `README.md` 的子项目索引表 | 替子项目写代码 / 写文档 |
| 写统筹文档（分工 / 依赖 / 优先级） | 把子项目的日志抄到父日志里 |
| 新建 / 归档子项目 | 在父项目根目录堆业务文件 |
| 维护本项目自己的规矩与钩子 | 跨到子项目树里改东西 |

**判据**：如果你正在写的东西是「某个具体问题的答案」，它就不属于父项目，
属于某个子项目。父项目只写「哪个问题归谁」。

### 2. 🔴 独立嵌套仓库：父仓库看不到子项目

`projects/` 整个被 `.gitignore` 排除，**每个子项目自己 `git init`，是完整独立的仓库**。

后果（必须知道，否则会以为是故障）：

- 父项目 `git status` 里**看不到任何子项目的改动**
- 子项目的事在子项目里提交
- 父项目只在自己的日志里记「新增 / 归档了哪个子项目」

不用 submodule / subtree 的理由：submodule 要在父仓库存子仓库的 commit 指针，
子项目每提交一次就得回父仓库更新指针——这与「父级日志只记父级」直接冲突，且极易忘、忘了就是脏状态；
subtree 则会把历史搅在一起，子项目没法独立迁走。

### 3. 🔴 父级日志只记父级

`CHANGE-LOG.md` 只记本项目自己的事：

| 该记 | 不该记 |
|---|---|
| 新建了一个子项目 / 归档了一个子项目 | 某个子项目内部加了个函数 |
| 改了统筹文档 / 调整了子项目之间的分工 | 某个子项目修了个 bug |
| 改了父项目自己的规矩 | 某个子项目升级了依赖 |

理由：子项目**根本不在父仓库的提交范围内**。硬往父日志里记，
写的是一份**没有对应提交的假历史**。

### 4. 新建子项目：七步，最后一步最容易忘

1. 判断类型（代码 / 实验 / 文档 / 父）——判据是**交付物长什么样**：
   能跑的东西 → 代码；一个结论 → 实验；要反复翻的知识 → 文档；管着一堆产出内容的 → 父项目
2. 找**复制源**，复制到 `projects/` 下并改名。按这个顺序找：
   ① 本项目 `projects/` 下同类型的现有子项目（首选，它已经贴合本项目的规矩）；
   ② 本项目里还没有同类型的 → 去**当初建本项目所用的那份模具**取对应类型的样板。
   🔴 模具在哪，写在本项目 `CHANGE-LOG.md` **最早那条立项记录**里；那里也没写就去问项目主人。
   **不要凭猜去找，更不要从零手搓一套骨架**——手搓的骨架一定漏钩子，而漏了钩子不会报错。
3. 清掉 demo 的示例内容，**保留骨架与格式示范**
4. 删 `.git/`，重新 `git init`
5. `git config core.hooksPath .githooks`
6. 改写子项目的 `README.md` / `CHANGE-LOG.md`；**不改它的 `HARNESS-STATUS.md`**（留给确立仪式）
7. 🔴 **回到父项目**：`README.md` 索引表加一行（含**状态**列，新建时填 🚧 进行中）
   + `CHANGE-LOG.md` 记一条 + 在父项目提交。
   🔴 **那条记录必须写明来由**：这个子项目因哪个需求 / 哪份调研 / 哪条实验结论而建（一句话就够）。
   来由是判断「它还该不该活着」的唯一依据——不写，半年后没人知道这个目录为什么存在。

⚠️ 第 7 步**没有钩子兜底**：父项目的 `pre-commit` 规则二本来管这个，
但 `projects/` 被 `.gitignore` 排除，所以它不会被触发。**这一步靠纪律。**

### 4b. 子项目的退场：放弃 ≠ 删除

🔴 **放弃一个子项目，不删目录、不移出 `projects/`、不清它的历史。**
「决定不做」本身是信息——它至少证明了这条路不通；删掉就等于这次尝试没发生过，
下一个人（或者半年后的你自己）会把同一条死路重走一遍。

两步走，各自按提交纪律留痕：

| # | 做什么 | 在哪提交 |
|---|---|---|
| 1 | `README.md` 索引表里这一行的状态改成 🗄 已放弃（留档） | 本项目，记一条父级 CHANGE-LOG |
| 2 | 子项目 `README.md` **顶部**加「放弃说明」：为什么停 / 验证到哪 / 若重启从哪接 | 子项目自己，记它自己的一条 CHANGE-LOG |

状态列只有四个取值：**🚧 进行中 · ⏸ 暂停 · ✅ 已完成 · 🗄 已放弃（留档）**。
它答的是**生命周期**（这个节点还活着吗），不是「能不能跑」——运行情况写进「是什么」列。

### 5. 什么时候该拆新子项目

| 该拆 | 不该拆 |
|---|---|
| 交付物形态变了（要结论 → 要能跑的东西） | 只是文件多了 |
| 纪律打架了（"只增不改" vs "测试是准入"） | 只是目录深了 |
| 它**可能被单独放弃**、需要独立的档案和历史 | 只是父项目的一个章节 / 一份文档（写进 `docs/`） |
| 大到没法交给另一个人独立推进 | —— |

后两个「不该拆」是**整理问题**，不是拆分问题。

🔴 **拆出来的每一个子项目，两头都要留痕**：往前留来由（第 7 步那条记录），
往后留结局（做完标 ✅ / 试不通标 🗄 并写放弃说明，见 §4b）。缺一头，这个节点就成了来由不明的孤岛。

## 干活纪律

提交时用 `git add <显式路径>`，**不要用全量形态**（`-A`、`--all`、裸点）——
本体系每次提交都要在 CHANGE-LOG 里对应一条记录，卷进来的东西没法写进那条记录。

`.githooks/pre-commit` 强制：改任何东西 → `CHANGE-LOG.md` 必须一起暂存；
`docs/` 有新增/删除/改名 → `README.md` 必须一起暂存。
🔴 日志必须**真的新增一行记录**——把本次说明改写进上一条记录那一行不算，闸门会拒。

启用钩子（clone 后一次）：`git config core.hooksPath .githooks`

### 边界

只写本项目树内的文件。🔴 **`projects/` 下的子项目树是别人的地盘**——
即便它们在你的目录里，也要走 `.claude/rules/boundary.md` §3 的授权流程。

### 🔴 在父项目会话里跨子项目干活：几个仓库，几次提交

一次会话里同时改了父项目和若干子项目（**不推荐**，但确实会发生）时，**提交不是一次，是几次**：

| 改动落在哪 | 在哪提交 | 谁把关 |
|---|---|---|
| 某个子项目的文件 | 到那个子项目目录里提交（`git -C projects/<名> ...` 或 `cd` 过去，都行） | 那个子项目自己的 `pre-commit`：要**它自己的** `CHANGE-LOG.md` 净增一条记录 |
| 父项目自己的文件（索引表 / 统筹文档 / 父日志） | 父项目根 | 父项目的 `pre-commit` |

钩子按仓库各自加载、各自生效，互不干扰；一次会话把几个仓库的提交都代办掉是允许的。
🔴 **但绝不能把子项目的改动提进父仓库**——`projects/` 被 `.gitignore` 排除是故意的：
不排除的话内嵌仓库会被父仓库记成一个 commit 指针（gitlink），子项目每提交一次、父仓库就得跟着更新一次指针。

🔴 **项目主人明确要求这么干的时候就照办**：按上面这张表把每个仓库各提交一次，
不要拿「边界」那一条一口回绝、也不要停下来反复要授权——他要的是活干完并且提交落对地方，不是一次拒绝。

🔴 **最容易漏的一步：父根的 `git status` 永远是干净的**，它看不见任何子项目的脏改动。
跨子项目干完活，**别拿父根的 `git status` 当「全都提交完了」的凭据**——它答的只是父仓库自己。
逐个仓库查（`git -C projects/<名> status --short`），或者在树根跑一次全树扫描：

```bash
find . -type d -name .git -not -path "*/.git/*" | while read g; do d=$(dirname "$g"); [ -n "$(git -C "$d" status --porcelain)" ] && echo "🔴 $d 有未提交改动"; done
```

没有任何输出 = 这棵树上所有仓库都干净。

⚠️ 还要知道：这样的会话**没跑过子项目的确立检查**，子项目的宪法也只在真的碰到它目录里的文件时才被带进上下文——
等于**拿父项目的规矩改子项目**。所以口径不变：**正式开发去子项目目录单开会话**；
这一节只管另一件事——**已经在父会话里改了，怎么把提交做对。**
