# demo-parent-project · 定时任务体系统筹

> **类型：父项目**（交付物 = 秩序，不是内容）。
> 双重身份：① 统筹「把散落的定时任务收拢」这一组工作；② **「父项目」范式的可复制样板**。
>
> **为什么存在**：因「定时任务散落在各服务的 crontab 里、失败没人知道」这个痛点而建——
> 而解决它要做三件性质完全不同的事（定方案 / 写实现 / 沉淀清单），塞进一个项目会让纪律互相打架，
> 所以先立一个父项目来管秩序，再按类型往下拆。
>

> 🔴 **它自己就在上一级总项目的 `projects/` 下，而它下面又挂着子项目——这就是递归。**
> 刚接手的 AI agent：读完本文去读项目根的 `CLAUDE.md`，再读 `docs/00-统筹说明.md`。

## 在统筹什么

现状：定时任务散落在各服务的 crontab 里，**失败没人知道、重跑靠登机器**。

解决它需要三件性质完全不同的事，所以要拆成不同类型的子项目：

| 要做的事 | 性质 | 该建哪类项目 | 现状 |
|---|---|---|---|
| 搞清楚选哪种调度方案 | 得出一个结论 | 实验项目 | 未建 |
| 把方案实现出来 | 交付能跑的东西 | 代码项目 | 未建 |
| 沉淀现有任务清单与口径 | 可反复引用的知识 | 文档仓库 | 未建 |

🔴 **不要因为"都是一个主题"就塞进一个项目**——类型不同则纪律不同，
硬塞在一起的结果是两套纪律互相打架，最后哪套都不执行。详见 `docs/00-统筹说明.md` §1。

> 父项目的价值在于先把秩序摆好，子项目按需要逐个建。

### 🔴 关于 `projects/` 的两件事

1. **它整个被本仓库 `.gitignore` 排除。** 每个子项目自己 `git init`，是完整独立的仓库。
   所以在这里 `git status` **看不到任何子项目的改动**——这是设计，不是故障。
2. **新建子项目后要手工回来更新上面的索引表**（+ 记一条 CHANGE-LOG）。
   父项目的 `pre-commit` 规则二本来管这个，但因为 `projects/` 被 ignore，
   git 看不到那次新增，**规则二不会触发。这一步靠纪律。**

## 怎么验证「嵌套是真的」

```bash
# 父项目和子项目是两个独立仓库，各有各的历史
git log --oneline
cd projects/mini-child-code-project && git log --oneline

# 子项目自己的钩子也是启用的
git config --get core.hooksPath        # 应输出 .githooks

# 子项目自己能跑能测
python3 -m pytest                      # 期望 12 passed
```
