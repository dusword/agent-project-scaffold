# 00 · 统筹说明

> 父项目的核心文档：**说清这一组子项目之间是什么关系、谁先谁后、边界在哪。**
> 判据：新来的人读完这份，能不能知道「我该去哪个子项目干活」？不能 → 没写够。

---

## 1. 这组项目在做什么

**主题：把散落的定时任务收拢成一个有人管的体系。**

现状是任务散落在各服务的 crontab 里，失败没人知道、重跑靠登机器。
要解决它，需要三件事，而这三件事**性质完全不同**，所以拆成不同类型的子项目：

| 要做的事 | 性质 | 该建哪类项目 |
|---|---|---|
| 搞清楚选哪种调度方案 | 得出一个结论 | 实验项目 |
| 把方案实现出来 | 交付能跑的东西 | 代码项目 |
| 沉淀现有任务的清单与口径 | 可被反复引用的知识 | 文档仓库 |

🔴 **不要因为"都是一个主题"就塞进一个项目。** 类型不同 → 范式不同 → 纪律不同。
实验项目的 `EXPERIMENTS.md` 只增不改，代码项目的测试是提交准入，
硬塞在一起的结果是两套纪律互相打架，最后哪套都不执行。

---

## 2. 子项目与分工

| 子项目 | 类型 | 交付物 | 状态 |
|---|---|---|---|
| `mini-child-code-project` | 代码项目 | 极简词频统计（**当前只是嵌套结构的示范**） | ✅ 可跑，12 测试全绿 |

> ⚠️ **现状说明**：这个父项目目前只挂了一个示范性质的子项目。
> 上面 §1 描述的三件事还没有对应的子项目建起来——**这是现状，不是遗漏**。
> 父项目的价值在于**先把秩序摆好**，子项目按需要逐个建。

---

## 3. 依赖与顺序

```
（未来）实验项目：调度方案选型
        ↓ 结论出来才好动手
（未来）代码项目：方案实现
        ↑ 需要输入
（未来）文档仓库：现有任务清单与口径   ← 这个可以并行做，不依赖任何人
```

🔴 **文档仓库那条线不阻塞任何人，应该最先开工**——
盘点现有任务是纯体力活，早做早有底，而且它的产出（任务清单）
恰好是实验项目需要的输入（要知道有多少任务、有没有依赖关系）。

**排期通则**：先做那些「不阻塞别人、又能给别人提供输入」的事。

---

## 4. 🔴 父项目自己的边界

父项目的交付物是**秩序**，不是内容。具体地说：

| 父项目该做 | 父项目不该做 |
|---|---|
| 维护 `README.md` 的子项目索引表 | 替子项目写代码 / 写文档 |
| 写本统筹文档（分工 / 依赖 / 顺序） | 把子项目的日志抄到父日志里 |
| 新建 / 归档子项目 | 在父项目根目录堆业务文件 |
| 维护本项目自己的规矩与钩子 | 跨到子项目树里改东西 |

### 为什么父仓库看不到子项目的改动

`projects/` 整个被父仓库 `.gitignore` 排除，每个子项目是**独立的 git 仓库**。

所以在父项目 `git status` 里看不到任何子项目的改动——**这是设计，不是故障**。
子项目的事在子项目里提交；父项目只在自己的日志里记「新增/归档了哪个子项目」。

### 一条要手工做的事

新建子项目后，**回到父项目**：
① `README.md` 索引表加一行；② `CHANGE-LOG.md` 记一条；③ 在父项目提交。

⚠️ 父项目的 `pre-commit` 规则二本来是管这个的，
但因为 `projects/` 被 `.gitignore` 排除，**它实际上不会被触发**。
**这一步靠纪律，请手动做。**

---

## 5. 什么时候该拆一个新子项目

| 信号 | 说明 |
|---|---|
| **交付物形态变了** | 从"要一个结论"变成"要一个能跑的东西" → 新建代码项目 |
| **纪律打架了** | 一个目录里既要"只增不改"又要"测试是提交准入" → 拆 |
| **有人接手不了** | 一个项目大到没法交给另一个人独立推进 → 拆 |

反过来，**不该拆**的信号：只是文件多了、只是目录深了。
那是整理问题，不是拆分问题。
