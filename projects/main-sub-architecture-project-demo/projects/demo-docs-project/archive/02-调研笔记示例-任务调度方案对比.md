> **日期**：2026-07-22

## 调研问题

内部有一批定时任务（日报生成、数据同步、清理），目前散落在各服务的 crontab 里。
问题很具体：**任务失败没人知道，重跑靠人工登机器。**

要选一个统一的调度方案。

---

## 三个候选

| 维度 | A：保持 crontab + 加监控 | B：轻量调度框架 | C：完整工作流引擎 |
|---|---|---|---|
| 失败告警 | 要自己写包装脚本 | ✅ 内置 | ✅ 内置 |
| 重跑 | 登机器手动跑 | ✅ 界面点一下 | ✅ 界面点一下 |
| 任务依赖（A 完成才跑 B） | ❌ 做不到 | 🟡 简单串行可以 | ✅ 完整 DAG |
| 历史执行记录 | ❌ 只有日志 | ✅ 有 | ✅ 有，含每步耗时 |
| 引入成本 | 极低 | 中（一个新服务 + 一个库） | 高（新服务 + 存储 + 学习曲线） |
| **运维成本**（🟡 主观） | 低但**隐性**：出事才发现没人管 | 中：多一个要看的服务 | 高：它自己就可能成为故障源 |
| 迁移成本 | 0 | 每个任务改一次启动方式 | 每个任务重写成 DAG 定义 |

---

## 观察到的几件事

1. **我们的真实痛点是"失败没人知道"，不是"依赖编排"。**
   现有任务里只有 2 个存在先后依赖，且都可以靠"合并成一个脚本"解决。
   🔴 按痛点选方案，别按功能表选——功能表永远是 C 最好看。

2. **C 的完整能力对当前规模是过剩的。** 分享会上提到，
   引入方自己也说前三个月主要精力花在"让调度器自己稳定"上。

3. **A 的成本是隐性的**：写包装脚本看起来只要一天，
   但"谁来维护这些包装脚本""告警发给谁""发了没人看怎么办"这些问题一个都没解决。
   **隐性成本容易被低估，因为它不出现在工时估算里。**

---

## 倾向（不是结论）

倾向 **B**：它正好覆盖真实痛点（告警 + 重跑 + 历史记录），
而没有为用不上的 DAG 编排付出代价。

🔴 **这是调研笔记，不是决策。** 真要定，还需要：

- [ ] 确认候选框架的具体选型（本笔记只谈了方案类型，没比具体产品）
- [ ] 试跑一个真实任务，量一下迁移工作量
- [ ] 确认告警接到现有的值班体系里，而不是新开一个通知渠道
