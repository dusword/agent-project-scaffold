# 灵感便签：归档编号会不会不够用？

> **日期**：2026-08-16
> **可信度**：⚪ 无——**这是一个想法，不是知识**。没有验证，没有依据。
> **状态**：📥 inbox 未归档。**灵感类材料可能永远不归档**，那也是正常结局。

## 想到的

现在 `archive/` 用两位数编号（`01-` `02-`）。要是以后攒到 100 份以上怎么办？
是不是应该一开始就用三位数？

## 顺着想下去的

- 三位数从第一天就丑，而且 99% 的仓库这辈子到不了 100 份。为了 1% 的可能性让 99% 的情况变难看，不划算。
- 真到了 100 份，问题恐怕也不是编号位数——**是这个仓库该拆了**。
  一个人翻 100 份文档找东西，本身就说明分类出问题了。
- 所以这可能是个**假问题**：编号不够用是症状，仓库该拆才是病。

## 更值得想的（这条才是真问题）

编号表达的到底是什么？现在混着两种含义：

| 含义 | 例 | 问题 |
|---|---|---|
| 归档的**先后顺序** | 先归档的拿 01 | 那它就只是个流水号，没信息量 |
| 阅读的**推荐顺序** | 最该先读的拿 01 | 那新归档的东西要插队，编号就得重排 |

**编号一旦定下不能重排**（别处引用会全部失效），所以第二种含义其实做不到。
那现在的编号实质上就是流水号——**如果是流水号，它就不该承担"该先读什么"的暗示**，
"该先读什么"应该由 README 索引表的**排列顺序**来表达。

## 结论

暂不改任何东西。**记下来是为了防止下次又想一遍。**

🔴 这份便签的价值不在结论（结论是"不改"），在于**它把一个假问题识别出来了**，
省得下次有人再花二十分钟纠结编号位数。

如果哪天真要动编号规则，先读这份。
