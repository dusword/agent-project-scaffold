# demo-docs-project · 知识仓库

> **类型：文档仓库**（交付物 = 可被反复引用的知识）。
> 双重身份：① 一个真的在用的知识仓库；② **「文档仓库」范式的可复制样板**。
>
> **为什么存在**：因为业务规则与调研笔记散在聊天记录和各人脑子里，**要引用时没人敢引**——
> 所以要有一个地方，把材料按「来源 / 日期 / 可信度」标清楚再沉淀下来。
> 它的交付物是**以后要反复翻的知识**，所以是文档仓库，不是某个项目的 `docs/`。
>

> 🔴 **刚接手的 AI agent**：**下面的索引表就是本仓库的全部目录。**
> 按需读其中一两份，**不要把整棵树读一遍**。规矩见项目根的 `CLAUDE.md`。

---

## 怎么用

```
inbox/      📥 随手扔进来的原始材料 —— 未整理、未核实，引用前先自己判断
archive/    ✅ 已整理、已编号 —— 可以直接引用
```

**新东西一律先进 `inbox/`。** 整理是有成本的，而大部分材料在被整理前根本不知道值不值得整理；
强行要求"进来就整理好"，结果是根本不往里放。

## 每份材料的头部长这样

```markdown
> **来源**：哪来的（会议 / 聊天 / 公开文档 / 自己想的）
> **日期**：YYYY-MM-DD
> **可信度**：🟢 高 / 🟡 中 / ⚪ 无 —— 并写清为什么是这一档
> **状态**：📥 inbox 未归档 / ✅ 已归档
```

| 档 | 含义 |
|---|---|
| 🟢 高 | 有权威出处，或经当事人确认过 |
| 🟡 中 | 一手信息但未核对，或部分主观判断 |
| ⚪ 无 | 想法、猜测、未验证的推论 |

🔴 **同一份文档里不同章节可信度不同时要分别标**——`archive/02` 就是例子：
功能对比来自官方文档（可信），运维成本一列是主观听感（不可信）。

## ⚠️ 一条要知道的局限

`.githooks/pre-commit` 的「结构变化必更 README」强制**只覆盖 `docs/` 和 `projects/`**，
而本仓库的内容全在 `inbox/` 和 `archive/`。

**所以这两个目录的索引同步靠纪律，不是靠钩子。** 加了文件就去改索引表，别等人提醒。

（为什么不改钩子：它是从模板继承的通用件，为单个项目改会导致各项目钩子分叉，
以后没法统一升级。详见 `.claude/HARNESS-STATUS.md` 末节。）

## 启用钩子（clone 后第一件事）

```bash
git config core.hooksPath .githooks

```
