# 一、设计决策

## D1 · git 用「独立嵌套仓库」，不用 submodule / subtree / 单一大仓库

**决策**：每个项目自己 `git init` 一个完整仓库；父仓库 `.gitignore` 忽略整个 `projects/`。

**为什么**：

- 每个仓库历史干净，可以**独立迁走 / 归档 / 交给别人**，不牵连任何其它项目。
- 代价只有一条：父仓库 `git status` 看不到子项目的改动。
  而这条代价**恰好就是我们想要的纪律**——「父级日志只记父级」。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| **git submodule** | 🔴 **与「父级日志只记父级」直接冲突**。父仓库要存子仓库的 commit 指针，子项目每提交一次，就得回父仓库更新一次指针并提交——而那次提交在父项目的 CHANGE-LOG 里**写不出一条有意义的记录**（「子项目动了一下」不是父级的事）。agent 极易忘更新指针，忘了就是脏状态。另外 clone 要 `--recursive`，坑深 |
| **git subtree** | 历史被搅在一起，子项目没法独立迁走。而「可独立迁走」正是本体系的核心诉求之一 |
| **单一大仓库** | 子项目之间历史互相污染；归档一个子项目要动全仓库历史；一个项目的 `.gitignore` / 钩子会波及所有项目 |

**已知代价（接受）**：同一份钩子在 N 个仓库里各有一份拷贝，**升级钩子要 N 处同步改**。
没有自动分发机制。这是「可独立迁走」换来的，本体系认这个账。

🔴 **2026-08-25 补一句，别读串了**：本条**维持原判**，它说的是**体系教给真实项目**的形态。
模具厂仓库自己已经转成单一仓库（展馆模式，**D11**）——那是它一个仓库自己怎么存历史，
与本条无关。翻案论证写在 D11 里（结论：真实项目场景下本条的三条否决理由全部仍然成立）。

## D2 · 宪法放项目根 `CLAUDE.md`，不放 `.claude/CLAUDE.md`

**决策**：每个项目的宪法一律是 `<项目根>/CLAUDE.md`；`.claude/` 只放
`HARNESS-STATUS.md` / `rules/` / `hooks/` / `settings.json`。

**为什么**：

- 项目根的 `CLAUDE.md` 是 Claude Code 官方文档**首要列出**的项目级位置，被长期承诺。
- 各版本、各衍生工具链都认根目录这一份，兼容性最好。

**否掉的替代**：`.claude/CLAUDE.md`。

🔴 **诚实记录**：实测**两个位置当前都生效**，`.claude/CLAUDE.md` 并没有坏。
否掉它的理由不是「它不работает」，而是「它**没有同等的书面承诺**」——
这套模板要被复制几十次、长期复用，**不能押在一个可能变的行为上**。

**踩过的坑**：早期两处都放了一份，结果**同一套指令被加载两遍**进上下文——
既浪费 token，又在两份内容不同步时产生自相矛盾的指令（Claude 可能任选其一执行）。
所以规范里写死了「绝对不许两处并存，要挪就 `git mv` 移动，不要复制」。

## D3 · 确立仪式用「记录的项目名 ≠ 目录名」触发，不写重置脚本

**决策**：`.claude/HARNESS-STATUS.md` 里记一行 `- 项目名：<目录名>`；
`harness-check.sh` 在 `SessionStart` 比较它和当前目录名，对不上就判「未确立」并注入仪式指令。

**为什么**：

```
demo-code-project/     记录「demo-code-project」= 目录名 → 安静
      ↓ 复制 + 改名
my-new-tool/           记录仍是「demo-code-project」≠ 目录名 → 自动触发仪式
```

**复制模板的动作本身就把状态弄「脏」了，而脏状态正是我们要的信号。**
所以这个机制的性质是：**不需要人记得做任何事，也就不可能忘记做。**

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 写 `scripts/reset-harness.sh`，复制后手工跑一次 | 🔴 **靠人记得跑 = 一定会忘**。而且忘了没有任何症状（状态文件写着「已确立」，钩子安静），坏在悄无声息 |
| 状态文件里放一个 `TEMPLATE_PLACEHOLDER` 占位符 | 效果类似，但复制后如果有人顺手把占位符填成别的名字（而不是当前目录名），机制就废了。用「目录名」做基准，**基准是环境给的，不是人填的**，更硬 |
| 每次开会话都跑一遍仪式 | 纯噪音。已确立的项目要求零输出，这是设计目标 |

**副作用（接受）**：给项目目录改名 = 重新触发一次仪式。
可接受——目录改名通常意味着定位变了，重新对一次规矩本来就该做。
真的只是改名，仪式里写「仅目录改名，规矩沿用」即可。

## D4 · 规矩靠钩子机器强制，但**局限如实写出来**

**决策**：三条关键规矩（改动必留日志 / 结构变化必更 README / 不许越界写）做成钩子；
同时在每个钩子的注释和文档里**写明它拦不住什么**。

**为什么**：

- 只写文字的规矩，agent 和人都会漂移。**没有牙齿的规矩等于呼吁。**
- 但假装钩子是铁桶更坏：会让人误以为「钩子没报错 = 没问题」，从而**停止人工审阅**。
  明说「`--no-verify` 绕得过去」「Bash 写文件绕得过去」，是为了保住人工审阅这道防线。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 只写规矩文档，不做钩子 | 已经验证过不行——文字规矩在长会话里必然漂移 |
| 做钩子但对外宣称「已完全强制」 | 会诱导人放弃审阅 diff。**假的安全感比没有安全感更危险** |
| 把钩子做到密不透风（拦 Bash、拦人工修改） | 做不到（人工改文件不经过工具层），且试图做到的过程会把正常工作卡死 |

## D5 · 四类项目范式，而不是一个通用骨架

**决策**：分「代码 / 实验 / 文档 / 父项目」四类，每类有自己的目录结构与纪律；
但**骨架文件（宪法位置、三个钩子、README/CHANGE-LOG 规矩）四类完全相同**。

**为什么**：

- 纪律必须贴合交付物形态。实验项目的核心资产是「只增不改的 `EXPERIMENTS.md`」，
  代码项目的核心是「测试是提交准入」——这两条互换就是灾难。
- 但骨架统一，才有「递归」和「随便复制哪个都能用」这两个性质。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 一个通用骨架，纪律靠项目自己写 | 每个新项目都要从零想一遍纪律，而想纪律恰恰是最容易偷懒的一步 |
| 每类一套完全不同的骨架 | 递归性没了；四套骨架各自演化，几个月后互相看不懂 |
| 更细的分类（前端 / 后端 / 数据 / 调研…） | 分类越细越判不准，判不准就会卡在选型上。四类的判据能用**一句话**说清，这是分类粒度的上限 |

**兜底**：判错不致命——骨架一样，改的只是 `CLAUDE.md` 的范式段落。

## D6 · boundary-guard 解析不出目标路径时，选择**放行**

**决策**：钩子解析 stdin 的 JSON 拿 `tool_input.file_path`（`jq` → `python3` → 正则三级兜底），
三级全失败时 **exit 0 放行**，而不是 exit 2 拦截。

**为什么**：

- 钩子的职责是**拦越界**，不是给正常工作添堵。
- 解析失败的最常见原因是「这次调用根本没有 `file_path`」（不是 Write/Edit，或参数形态变了），
  这类调用**本来就不该被拦**。
- 若选择「解析失败即拦截」，一旦 Claude Code 改了钩子协议的 JSON 结构，
  **所有 Write/Edit 会全线瘫痪**，而且报错信息是「越界」——指向完全错误的方向，极难排查。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 解析失败即拦截（fail-closed） | 协议一变就全线瘫痪，且错误信息误导。**代价不对称**：误拦的损失（工作停摆 + 排查困难）远大于漏拦的损失（越界写入还会在对方仓库的提交硬闸被拦一次） |
| 解析失败时打警告再放行 | 试过，噪音大且没人看。真要防这个，该做的是**版本升级后重跑一次自测**，不是每次都喊 |

🔴 **这是一个明确的 fail-open 选择，写在这里就是为了别人能翻案。**
翻案的前提是先给出「协议变化时如何不瘫痪」的方案。

**兜底为什么够**：越界写入无论怎么进来，最终都要在**对方仓库的 `pre-commit`** 被要求留下日志。
拦截器是第一道，对方的硬闸是第二道，人工审阅 diff 是第三道。

## D7 · 自动化脚本全部暂缓（`new-project.sh` / `check-all.sh` / `sync-index.sh`）

**决策**：新建项目、全量体检、索引同步三个脚本**都不写**，现阶段用文字步骤清单。

**为什么**：

- 现阶段项目数量少，**手工做一遍能让人真正记住机制**——而这套机制的每一步都有理由，
  记住理由比省那几分钟值钱得多。
- 脚本写早了会变成「不知道它替我做了什么」的黑盒。用户遇到问题时**无法判断是自己错了还是脚本错了**。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 先把 `new-project.sh` 写了 | 复制 + 改名 + init + hooksPath + 清示例，五步里有四步需要**按项目情况判断**（清哪些示例、留不留某个 demo），脚本要么问一堆问题，要么替你瞎猜 |
| 写个只做机械部分的薄脚本 | 机械部分就是 `cp -R` + `rm -rf .git` + `git init` + 一行 config，**四条命令**。包一层的收益抵不上多一个要维护的东西 |

**什么时候该重新评估**：等手工步骤跑顺、**痛点明确**（比如「每次都忘第 9 步」反复发生），
再针对那个具体痛点写脚本。**不要先写脚本再找用途。**

🔴 **不要自作主张先把脚本写了。**

## D8 · 说明书与成品分家（本项目的立项理由，2026-08-19）

**决策**：把「关于模板怎么用 / 怎么设计」的文档，从模板成品里**全部搬出来**，
放进一个独立的父项目 `agent-project-scaffold`（模具厂）；
成品 `main-sub-architecture-project-demo` 移到它的 `projects/` 下，改造成**出厂纯净**的示范项目。

**为什么**：

模板成品会被复制几十次，**复制出去的每一份都会带上它内部的所有文档**。
说明书写在成品里，三个后果：

| 后果 | 说明 |
|---|---|
| 新项目一出生就带着一份**不属于它**的说明书 | 用户得手工删；忘了删就永远留着误导后来的 agent |
| 成品既是示范又是教材，**两种口吻打架** | 示范该演示「一个正常项目长什么样」，教材要讲「模板怎么用」。写在一起两边都不像 |
| 模板的**开发史**混进示范史 | 「补架构规范 + 修 pre-commit 的 bug」是模具厂的事。一个正常总项目的 CHANGE-LOG 里不该出现这种记录 |

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 说明书留在成品里，在 README 写「复制后请删除 docs/00-架构规范.md」 | 靠人记得删 = 一定会忘（同 D3 的理由）。而且忘了没有症状 |
| 说明书放成品的一个 `_template-docs/` 目录，靠 `.gitignore` 排除 | 排除了就不进版本管理，说明书自己没了历史；而且 `cp -R` 照样会复制过去 |
| 说明书写进成品的 `CLAUDE.md` 顶部注释 | 宪法是给项目干活用的，塞进教材内容会让每个新项目的宪法都带一段废话进上下文 |

**代价（接受）**：钩子和规矩现在有**两份**（模具厂一份、成品一份），改了要两边同步。
这是 D1「独立嵌套仓库」的既有代价，不是新增的。规范里已写死「规范与成品必须同步」这条纪律。

**顺带定下的 README 新标准**（两个父项目的 README 按此重写；
五个子项目 README 逐条核对后**原本就满足**——各有自我介绍 + 完整索引表 + 无绝对路径，故未改动）：
**开头两三段自我介绍（我是谁 / 交付什么 / 怎么维护），主体是目录指引表，对人和 agent 都友好。**
理由：agent 靠索引表决定读哪个文件；人靠开头几段决定要不要继续读。**只有表没有介绍，人读不下去；只有介绍没有表，agent 只能把整棵树读一遍。**

## D9 · 愿景层文档补齐：生命周期状态 / 放弃留档 / 来由追溯 / 拆分判据（2026-08-19）

**依据**：项目主人 2026-08-19 的愿景陈述（原话已逐字收进
[`00-架构规范.md`](00-架构规范.md) §0）。要点三句：
父子架构是**对任务的拆解**；调研会不断催生尝试性方向；
**尝试可能放弃，但必须留档**，且「不希望它们一个一个项目毫无联系散落在各处」。

**审计发现的缺口**：递归机制、实验项目的「导出新方向」、文档项目的「永不归档也是正常结局」
这三样**本来就在**。缺的全在愿景层——**体系写清了「怎么做」，没写「为什么是这个形状」**：

| 缺口 | 补了什么 | 落点 |
|---|---|---|
| 一 · 立法意图缺失 | 「这套架构为了什么」四条意图 + 原话 + 那条真实的拆解链（PM 提效 → 工作台 → 商品指纹） | 规范 §0 · 本项目 README 定位段 · 成品宪法定位段（精炼版） |
| 二 · 子项目没有生命周期 | 状态四态（🚧 进行中 / ⏸ 暂停 / ✅ 已完成 / 🗄 已放弃（留档））+ **「放弃不删」铁律** + 放弃说明三句话模板 + 父项目索引表必须有状态列 | 规范 §2.4 · 两份父项目宪法「子项目的退场」· 三份父项目 README 索引表 |
| 三 · 来由不可追溯 | 七步第 7 步升格为「必须写来由」；索引表「是什么」列带来由；子项目 README 自我介绍必须答「为什么存在 / 源自哪里」 | 规范 §5 · 两份宪法七步 · 7 份 `docs-discipline.md` · 五个 demo 的 README |
| 四 · 「何时该拆」只有零散判据 | 三条判据（自己的交付物与生命周期 / 可能被单独放弃 / 需要独立档案，占两条就拆）+ 反例 + **调研 → 拆分闭环**那条链 | 规范 §2.5 · 成品 `docs/00-项目说明.md` §5 |

**为什么这四块非补不可**：

- 状态与来由是**树上每个节点的两条元信息**。缺状态 → 一棵看不出死活的树；
  缺来由 → 半年后没人知道某个目录为什么存在。两样都缺，树就退化成「散落各处」，
  正好是这套架构要解决的那个问题。
- **「放弃不删」必须写成铁律而不是建议**：删目录是个一步就能做完、事后无法挽回的动作，
  而它删掉的是「这条路不通」这条最容易被重复踩的知识。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 只在使用指南里写「建议给子项目标个状态」 | 建议不会被执行。状态列写进**README 标准**才有人填，而 README 是 agent 读的第一份东西 |
| 放弃的子项目移到 `archive-projects/` 目录 | 移出去就断了它和父项目索引表的关系，等于**换个地方散落**。留在原位改状态，父项目一眼看得到「这里试过、没成」 |
| 放弃时只在父项目 CHANGE-LOG 记一条，子项目不写说明 | 父日志那一行写不下「验证到哪 / 若重启从哪接」；而这两句恰恰是重启时唯一有用的东西 |
| 给状态列加更多态（调研中 / 待验收 / 冻结…） | 态越多越判不准，判不准就没人填。四态覆盖「活着 / 停了 / 完了 / 死了」，是能一眼选中的粒度上限（同 D5 的分类粒度理由） |

**代价（接受）**：放弃的子项目会一直占着目录和一份 harness。
这是刻意的——**占地方正是它留档的方式**。

## D10 · 唯一一个脚本：`scripts/init-repos.sh`（因公开分发而生，2026-08-19）

**决策**：为「从 GitHub 拿到本模板」这条路径写一个脚本
[`../scripts/init-repos.sh`](../scripts/init-repos.sh)——从仓库根往下找出每个项目单元
（判据：目录里同时有 `CLAUDE.md` 和 `.githooks/`），给还没有 `.git` 的那些
`git init` + 启用提交硬闸 + 做一次首次提交。幂等，重复跑无副作用。

**🔴 这不是推翻 D7。** D7 暂缓的是三个**建项目**的脚本
（`new-project.sh` / `check-all.sh` / `sync-index.sh`），它们至今一个都没写，暂缓照旧。
本脚本解决的是一个 D7 当时**还不存在的问题**：

| | D7 暂缓的那三个 | 本脚本 |
|---|---|---|
| 解决什么 | 建新项目 / 体检 / 同步索引 | 把**压平的分发快照**还原成独立嵌套仓库 |
| 需要判断吗 | 🔴 要。清哪些示例、留不留某个 demo、索引怎么写，都得看项目情况 | **不需要**。找单元的判据是机械的，每个单元做的四件事一模一样 |
| 手工替代方案 | 四条命令，包一层不值 | **7 个仓库 × 4 步 = 28 步**，且漏一步不报错（漏 hooksPath 就是硬闸静默失效） |
| 不写会怎样 | 没事，手工做一遍还能学到机制 | 🔴 **分发直接不可用**：clone 下来一个 `.git` 都没有，整套纪律全体失效 |

D7 的判据原话是「**手工做一遍能让人真正记住机制**」——那条对「建项目」成立（每一步都有理由要记），
对「把 7 个仓库建回来」不成立：重复 7 遍同样的四条命令记不住任何东西，只会漏。
而 D7 还说了「等痛点明确再针对那个具体痛点写脚本」，**这就是那个明确的痛点**。

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| 不写脚本，在 README 里写「请对这 7 个目录各跑 4 条命令」 | 28 步手工操作，且**漏了不报错**。尤其 `core.hooksPath` 漏一个，那个仓库的提交硬闸就静默失效——正是本体系最怕的那类故障（同 D3 的理由：靠人记得做 = 一定会忘） |
| 用 git submodule 分发，clone 时 `--recursive` 就能拿到 7 个仓库 | 这是 D1 已经否掉的方案，不能为了分发方便把架构本身换掉 |
| 只发布模具（`main-sub-architecture-project-demo`），不发布模具厂 | 那就把三份说明书（规范 / 使用指南 / 设计决策）扔了——而 D8 的全部理由就是这三份说明书必须存在、且必须与成品分家 |
| 脚本顺手把「复制改名建新项目」也做了 | 那才是真的推翻 D7。**刻意不做**：本脚本只做还原分发形态这一件机械事，一步不多 |

**已知代价（接受）**：`git clone` 下来的那一份，根仓库**已经在跟踪 `projects/` 下的文件**
（快照里它们是普通文件，而 git 对已跟踪文件不再看 `.gitignore`），
于是根目录 `git status` 能看见子项目的改动——与本体系「父仓库看不见子项目改动」不一致。
脚本在结尾**只在真的检测到这种重叠时**才打印这条提醒，并给出两条清理路径（zip 下载 / `git rm -r --cached projects/`）。
这条代价只落在分发的那一份上；照使用指南复制模具建出来的项目行为完全正确。
详见 [`03-发布与同步.md`](03-发布与同步.md)。

🔴 **分发形态随 D11 变了**：本仓库自己已转为单一仓库，所以
[`../scripts/init-repos.sh`](../scripts/init-repos.sh) 现在**只还原根仓库一个**，
上面这段「根仓库跟踪 `projects/`」的代价也不再是代价（在展馆模式里那本来就是对的）。
上面那张对照表里「7 个仓库 × 4 步 = 28 步」的算法随之缩水成 1 个仓库 4 步，
但**脚本存在的核心理由一个字没变**：`core.hooksPath` 是仓库的**本地配置**，
zip 下载没有 `.git`、`git clone` 有 `.git` 却带不来这份配置——**两种拿法都缺它，
而缺了不报错**，正是本体系最怕的那种静默失效。

## D11 · 模具厂**自身**转单一仓库（展馆模式），体系架构维持 D1（2026-08-25）

**决策**：分成**互不相干**的两句，读的时候千万别合并：

| | 本仓库 `agent-project-scaffold` 自己 | 体系教给真实项目的架构 |
|---|---|---|
| git 形态 | 🔴 **1 个仓库装 7 个项目单元**（展馆模式） | 🔴 **独立嵌套仓库**，每个项目自己 `git init`，父仓库 `.gitignore` 排除 `projects/` |
| 依据 | 本条 D11 | **D1，维持原判，一个字没改** |

**背景**：2026-08-24 做了一轮 monorepo 评估（起因是维护 7 个仓库的实际摩擦：
钩子改一次要同步 7 份、看全树状态要写循环、备份要各推各的）。评估没有靠推理下结论，
跑了**五路证据**：

| # | 这一路验什么 | 结果 |
|---|---|---|
| 1 | **官方文档查证**：单仓子目录里，Claude Code 的规矩装置还认不认 | 钩子与宪法按**会话启动目录**解析，`CLAUDE.md` 沿目录树**向上**逐级加载——两者都**不看 git 仓库边界**。也就是说「一个项目一个仓库」从来不是 harness 生效的前提 |
| 2 | **子目录 harness 实测**：把上一条真的跑一遍 | 在单仓的子目录里开会话，**确立仪式照常触发、越界拦截照常工作**，与独立仓库时无差别 |
| 3 | **路径感知硬闸原型**：单仓下「按单元记账」能不能机器强制 | 原型 **18 项测试全过**。同一轮还实测了旧钩子：单仓形态下**子单元的改动可以拿仓库根的日志顶包，闸门零告警放行**——这不是理论风险，是当场复现的（后来落成 v2，见 `00-架构规范.md` §6.1） |
| 4 | **真实 7 仓移植彩排**：历史能不能不丢地并进来 | 路径改写后合并 **76 + 6 = 82 条提交零冲突**；**叶子树对象逐字节一致**（说明改写只动了路径、没动内容）；`subtree split` 逃生舱验过——真要拆回去，任一单元的提交可完整复原 |
| 5 | 🔴 **红队对抗**：多 agent 并行时，单仓扛不扛得住 | **扛不住**。8 个并行会话共 64 次提交**只活下来 8 次**，`index.lock` 报错 **98 次**，而且**存活的 8 次里有 6 次混进了别人的文件**。这一路是整个评估里分量最重的一条 |

**为什么（结论一：体系维持 D1）**：

「每个小问题单独是一个项目」这句话里，真正**硬**的只有三样：

1. **独立的提交单位**——一次提交只属于一个项目；
2. **独立的提交身份**——谁改的、以什么身份改的，各记各的；
3. **独立、可验证的账本**——「提交条数 = 日志记录行数」这个不变量能单独核对（L7）。

这三样**是仓库边界给的**，不是目录结构给的。而第 5 路证据说明：多个 agent 并行干活时，
**共享一个暂存区是结构性风险**（`git add` / `git commit` 抢同一个 index，锁冲突之外还会互相把文件卷进去）。
真实项目正是要并行的那种场景，所以**体系层面维持 D1，一个字不改**。

**为什么（结论二：本仓转单仓）**：

本仓库恰好**不在**那个场景里：

| 本仓库的实况 | 因此 |
|---|---|
| **单维护者**，没有多 agent 并行往同一棵树里写 | 第 5 路的结构性风险在这里不成立 |
| `projects/` 下的模具与 demo 是**展品**，不是并行工地——它们的职责是「被复制走」，不是「被并行开发」 | 它们不需要各自的仓库边界，需要的是**总在一起、总同步** |

换来四件实在的好处：

| 换来什么 | 说明 |
|---|---|
| **钩子运行时只剩一份** | 改一次钩子，全树立刻生效，不用同步 7 份（D1 那条「已知代价」在本仓消失了） |
| **一条 `git status` 看全树** | 不用再写 `find . -name .git` 的循环去扫有没有漏提交的仓库 |
| 🔴 **规范 ↔ 模具原子同步** | 「改了规范就要同步改成品」（宪法纪律三）现在可以**放进同一次提交**里完成。以前这是两个仓库两次提交，中间那一刻文档与成品是不一致的，而**不同步的规范比没有规范更坏** |
| **一个私有 remote 全量备份** | 备份从「7 个仓库各推各的」变成一次推完，漏掉一个的可能性归零 |

**否掉的替代**：

| 方案 | 否掉的理由 |
|---|---|
| **全体系改 monorepo**（把 D1 也一起翻掉） | 🔴 第 5 路红队证据直接否掉：64 次提交存活 8 次、98 次 `index.lock`、存活的还混进别人的文件。真实项目要多 agent 并行，共享暂存区是**结构性**风险，不是调优能解决的 |
| **维持 7 个仓库，只把钩子改成共享 `core.hooksPath`** | 可行，也确实能省掉「钩子改 7 份」。但它**解决不了另外两件**：规范与模具的**原子同步**（仍然是两个仓库两次提交）、备份的**聚合**（仍然是 7 个 remote）。为一个小痛点引入一份非常规配置，换不来主要收益 |
| **submodule / subtree** | 🔴 **再次否决，理由与 D1 当年一样**：submodule 要父仓库存子仓库的 commit 指针，与「父级日志只记父级」直接打架；subtree 把历史搅在一起且**子树历史在路径过滤下会失明**（这次移植彩排里实测到了，见 L9）。两者都比「直接放进来当展品」更复杂、更容易出脏状态 |

**已知代价（接受）**：

| 代价 | 说明 |
|---|---|
| 🔴 **本项目不再用自己的身体示范「独立嵌套」** | 以前「这套架构第一次真实使用就是装它自己」这句话对**每一条**都成立，现在 git 形态那一条是例外。**示范职责移交给模具**：模具与它下面的 demo 仍然按独立嵌套写文档（它们的 `.gitignore` 里那行 `projects/` 是**出厂形态**，不许改），复制走的人拿到的仍然是 D1 那套 |
| 🔴 **本仓的 git 历史永远不可以直接 push 到公开仓库** | 单仓之后「一个仓库一份历史」听起来像是可以直接推了，但**不许**——出口安检只扫工作区、不扫历史。这条已经写成 [`03-发布与同步.md`](03-发布与同步.md) §1 的铁律，来龙去脉见 **L11** |
| **两套口径要一直分开说** | 根 `CLAUDE.md`、`README.md`、三份说明书里凡是提到 git 形态的地方，都得写清「这是本仓的 / 这是教给你的」。这是文字成本，靠的是 L8 那条纪律：改一条口径就 `grep` 全仓库一处改处处改 |
| **模具子树的新文件会被 `.gitignore` 挡下** | 模具自己的 `.gitignore` 排除 `projects/`，而本仓要跟踪它——往那些子树**新增**文件必须 `git add -f`。用显式路径漏了会报错、用宽泛 pathspec 漏了才无声无息；另有一个「已跟踪文件也照样警告 + 退出码 1」的摩擦。三种形态见 **L10** |

**迁移是怎么做的（留给以后要翻案或要拆回去的人）**：

| 步骤 | 做法 |
|---|---|
| 历史并进来 | 每个子仓库先用 `filter-branch` 做**路径改写**（把提交里的路径整体挪到它在本仓的位置），再 `merge --allow-unrelated-histories` 接进来。6 个子仓 = 6 个 merge 提交 |
| 为什么不用 `subtree add` | 它接进来的历史**在路径过滤下失明**（`git log -- <路径>` 看不见），等于账本核对不了。实测见 **L9** |
| 回滚锚 | tag **`pre-monorepo-2026-08-25`**，指向迁移前的最后一条提交 |
| 旧仓库留档 | 6 个嵌套 `.git` 原样移到 `.migration-backup/nested-git/`（**只在本机**，`.gitignore` 已排除，也在 rsync 排除清单里——它本身就是一堆 git 历史，让它出境等于绕开 L11 那条铁律） |
| 账本怎么对 | merge 提交**豁免**于「提交数 = 记录行数」这个不变量：那 6 个 merge 不代表任何单元的一次改动。按单元核对的命令写在根 `CLAUDE.md` 里 |

**按翻案规则如实说明**（本文末尾「附：翻案怎么翻」要求的那一条）：
本条**重新论证了 D1 当年否掉的「单一大仓库」**。D1 给的否决理由是三句：
「子项目之间历史互相污染 / 归档一个子项目要动全仓库历史 / 一个项目的 `.gitignore` 与钩子会波及所有项目」。
重新论证的结果是**分层的**：

- 在**真实项目**的场景里（多 agent 并行、子项目要能独立迁走），这三句**仍然成立**，
  而且第 5 路证据又给它加了一条更硬的理由（共享暂存区）。**所以 D1 维持原判。**
- 在**本仓库**这个场景里（单维护者、展品不并行、模具本来就该跟规范一起走），
  三句各自的分量都变了：历史「互相污染」在展馆里恰恰是「总在一起」；
  归档展品不需要动历史（它就没打算被独立迁走）；`.gitignore` 与钩子的波及范围
  由路径感知硬闸 v2 按单元隔开了。**所以本仓例外采纳。**

**一句话记法**：**规矩没改，改的是模具厂自己怎么存历史。**

# 二、开发教训与已知局限

## L1 · 🔴 git 默认转义非 ASCII 路径，中文文档名会躲开钩子的前缀匹配

**症状**：`pre-commit` 规则二（`docs/` 结构变化必须同步 README）对中文文件名**完全不生效**，
而且一声不吭——提交顺利通过，README 没更新，索引悄悄失真。

**根因**：git 默认开着 `core.quotepath`，输出路径时把非 ASCII 字符转义并加引号：

```
docs/00-架构规范.md   →   "docs/\346\236\266\346\236\204\350\247\204\350\214\203.md"
```

钩子里 `^docs/` 的前缀匹配，因为路径开头多了一个 `"` 而**永远匹配不上**。

**修法**：所有读取暂存区的命令都带上 `-c core.quotepath=false`：

```bash
git -c core.quotepath=false diff --cached --name-status -M
```

并在 awk 里加一层兜底 `unq()`，把仍带引号的路径去掉首尾引号。

**教训（这条比 bug 本身重要）**：

🔴 **本体系的文档文件名约定就是中文**（`docs/01-需求.md`）。
也就是说，这个 bug 命中的**不是边角情况，是主路径**——
规则二在被发现之前，对本体系**绝大多数文档**都是形同虚设的。

推广一下：**钩子里凡是拿路径做字符串匹配的地方，都要先确认工具输出的是原始路径还是转义路径。**
这个 bug 是在写规范、给钩子做机械自测时才发现的——**说明「写下来」这个动作本身就在找 bug**。

---

## L2 · 🔴 状态检测用全文匹配，被文档自己的说明文字误触发

**症状**：一个明明已经确立过的项目，每次开会话都被判成「harness 尚未确立」，
天天弹一遍仪式指令。

**根因**：`harness-check.sh` 早期版本判定条件之一是：

```bash
grep -q "未确立" "$status_file"        # ❌ 全文找关键词
```

而 `HARNESS-STATUS.md` 里正常的**说明性散文**大量出现这三个字：

- 文件头部：「否则会被判定为**未确立**并触发确立仪式」
- 文件末节：「两者对不上 → 下次开会话自动触发确立仪式…一旦被复制改名就自动变回**未确立**」

于是文件写得越清楚，越容易被自己误判。

**修法**：改成**行首锚定 + 完整前缀**匹配，并把状态行的写法定成约定：

```bash
grep -q "^## 当前状态：未确立" "$status_file"        # ✅ 锚定行
```

```markdown
## 当前状态：已确立        ← 状态只许写在这一个位置，二选一，一字不差
```

**教训**：

🔴 **检测词只要会出现在文档的散文里，全文匹配就一定会误报。**

这类 bug 的形状很固定：**状态用「文件里有没有某个词」表达**。
正确做法是让状态有一个**明确的、结构化的位置**（行首锚定的标题、固定前缀的字段、专门的一行），
散文区和状态区**物理分开**。

同样的形状在本体系里出现过两次——另一次是 `- 项目名：` 那一行，
它从一开始就用 `sed -n 's/^- 项目名：...//p'` 做**行首锚定 + 前缀解析**，所以没出过问题。

---

## L3 · 局限：父项目「新增子项目要更新索引」没有钩子兜底

**局限**：`pre-commit` 规则二写的是「`projects/` 下有新增/删除/改名 → README 必须一起暂存」，
但 `projects/` 被父仓库 `.gitignore` 排除了。
**git 根本看不到那次新增，规则二永远不会因为 `projects/` 触发。**

**所以这条规则里的 `projects/` 分支，实际上是一段死代码。**

**为什么不修**：

| 备选修法 | 否掉的理由 |
|---|---|
| 不 ignore `projects/`，改成只 ignore 里面的内容 | 那就回到「父仓库能看见子项目改动」，D1 的整个前提没了 |
| 钩子里改成扫文件系统（`ls projects/`）和 README 索引表比对 | 钩子要解析 markdown 表格，脆；且父项目在做别的提交时也会被拦，噪音大 |
| 删掉规则二里的 `projects/` 分支 | 🔴 **刻意保留**。留着它，等于在代码里留下「这件事本该被强制」的声明；真哪天 ignore 策略变了，规则立刻生效 |

**现状处理**：**靠纪律 + 文档明说**。
`01-使用指南.md` §4.2 第 9 步、各父项目 README 的「关于 `projects/` 的两件事」，
都明确写了这一步没有机器兜底、必须手动做。

## L4 · 局限：`pre-commit` 规则二只覆盖 `docs/` 和 `projects/` 两个前缀

**局限**：规则二的路径匹配写死了两个前缀。**其它目录的结构变化不会要求同步 README**，例如：

| 项目类型 | 不被覆盖的目录 |
|---|---|
| 文档仓库 | `inbox/` · `archive/`（**而这是它的全部内容**） |
| 代码项目 | `src/` · `tests/` |
| 实验项目 | `experiments/` |

文档仓库受影响最重——它的索引表是 README 的主体，却完全没有机器兜底。

**为什么不按项目类型定制**：

钩子是**从模板继承的通用件**。为单个项目改它，会导致各项目的钩子分叉；
分叉之后，本体系已经付了「N 个仓库各有一份钩子拷贝」的代价（D1），
再加上内容也不一样，**以后就没法统一升级了**。

**为什么不干脆覆盖所有目录**：

会把噪音拉到不可用——代码项目每加一个源文件、实验项目每存一份数据，都要动 README。
**规则二的价值在于「结构变了索引会失真」，而不是「文件多了一个」**，
`docs/` 和 `projects/` 是这个价值最集中的两处。

**现状处理**：在受影响的项目 README 里**明确写出这条局限**（成品的 `demo-docs-project` README 就有一节专门讲这个），
让读到的人知道这里靠纪律，不要误以为有机器在管。

## L5 · 🔴 提交硬闸规则一漏了 `README.md`，而自测用例恰好只测了这一个文件

**症状**：只改 `README.md` 提交，**不要求留 CHANGE-LOG**，一声不吭就过了。
规则一——本体系最硬的那条保证——对纯 README 改动**整个失效**。

**根因**：路径分类的 `case` 每条路径只落进一个桶：

```bash
case "$p" in
  CHANGE-LOG.md) changelog_staged=1 ;;
  README.md)     readme_staged=1 ;;      # ❌ 没同时置 other_staged
  *)             other_staged=1 ;;
esac
```

而规则一判的是 `other_staged`。`readme_staged` 本来是给**规则二**用的
（结构变化时检查 README 有没有一起暂存），两条规则共用一套分类，结果 README 被规则一漏掉了。

钩子自己的注释写得很清楚：「只要有任何**非 `CHANGE-LOG.md`** 的文件进入暂存区，
`CHANGE-LOG.md` 就必须一起进入」。**实现和自己声明的口径不一致**——这是 bug，不是设计。

**修法**：让 `README.md` 同时置两个标志。

```bash
README.md)     readme_staged=1; other_staged=1 ;;
```

**教训（这条最扎心）**：

🔴 **写在文档里的自测命令，一直是错的，而且没人发现。**

规范里的钩子自测清单第一条就是：

```bash
echo x >> README.md && git add README.md && git commit -m "test"   # 注释写着「应当被拒绝」
```

**它从来没被拒绝过。** 自测清单被当成「写下来就等于验证过了」，而没有人真的跑一遍看结果。

两条推论：

1. **自测用例挑的文件，恰好是唯一有豁免的那个** ——
   这不是运气差，是**用例设计时只想着「随便改个文件」，而 README 是最顺手的那个**。
   挑用例要**刻意覆盖分类的每个分支**，尤其是有特判的分支。
2. **「已自测通过」这句话必须有证据**。没贴出实际输出的自测，等于没测。
   本次重组时逐条重跑，才发现这个洞——**跑一遍的成本，远低于一条假保证造成的损失**。

同一形状的坑本文里已经出现三次（L1 中文路径没测、L2 说明文字误触发没测、L5 README 豁免没测），
共同点都是：**代码写完了，文档写完了，唯独没有把文档里那条命令真的敲进终端。**

## L6 · 🔴 局限：boundary-guard **拦不住「父项目改子项目」**——而这正是最常发生的越界方向

**事实**（2026-08-19 实测）：在父项目会话里 `Write` 一个子项目的文件，钩子**放行**。

```
CLAUDE_PROJECT_DIR = <父项目>
目标               = <父项目>/projects/demo-code-project/README.md
判定               = 在项目树内 → exit 0（放行）
```

**为什么**：钩子的判定标准是「目标是否在 `$CLAUDE_PROJECT_DIR` 这棵树里」。
子项目**物理上就在父项目树里**（`projects/<子项目>/`），所以它天然满足「在树内」。

🔴 **讽刺的是**：`.claude/rules/boundary.md` §1 的越界清单第一条就是「改隔壁子项目的源码 / 文档」，
而钩子恰恰**不管这一条**。规矩写了，牙齿没长在这儿。

**这条曾经被写成假的**。重组时我在两个地方写过「在本项目会话里改子项目，`boundary-guard.sh` 会拦」——
**实测是错的**，已改成如实说明。这正是 D4 说的那件事：
**假的安全感比没有安全感更危险**，因为它会让人停止人工审阅。

**为什么现在不修**：

| 备选修法 | 评估 |
|---|---|
| 钩子加一条：目标落在 `projects/*/` 下就拦 | 技术上简单。但这是**扩大用户可见的行为边界**——从「拦树外」变成「树内也拦一部分」，属于需要项目主人拍板的改动，不是 bug 修复 |
| 靠子项目自己的 `pre-commit` 兜底 | 已经在兜了：越界写入无论怎么进来，提交时都会被**对方仓库**要求补它自己的 CHANGE-LOG。这是现有的第二道防线 |
| 什么都不做，只把事实写清楚 | ✅ **当前选择**。规矩仍要求「去子项目目录开会话改」，但明说它没有机器兜底 |

**现状处理**：父项目的 `CLAUDE.md`、`00-架构规范.md` §6.2、`01-使用指南.md` §6/§7
四处都已改成如实表述。**要不要给钩子加这条拦截，留给项目主人决定。**

### 附带发现：放行条前缀的符号链接不对称（小坑，不影响实际使用）

`abspath()` 解析目标路径时会用 `pwd -P` 解开**父目录**的符号链接，但放行条那一行的**最后一段**不解。
macOS 上表现为：放行条写 `/tmp`，目标 `/tmp/x.txt` 被解析成 `/private/tmp/x.txt`，**前缀对不上，仍被拦**。

实测**不影响真实用法**——放行条通常指向隔壁项目目录（`../demo-docs-project/inbox`），
这类路径不是符号链接，前缀匹配正常（已验证：授权目录内放行、目录外仍拦）。
记在这里只为下次有人拿 `/tmp` 做自测时不困惑。

## L7 · 🔴 提交硬闸只验「日志在场」，不验「日志真的多了一条」——被一个正常会话自然打穿

**症状**（2026-08-19 真实会话模拟测试中自然发生，不是构造的）：
一个无头会话改 `CHANGE-LOG.md` 时，用 Edit 把这次的说明**揉进了上一条记录那一行**。
文件确实变了、也确实进了暂存区，`pre-commit` **照常放行**。结果：

```
git log 5 次提交   vs   CHANGE-LOG 4 行记录
```

`CHANGE-LOG.md` 自己开头就声明「一条记录 = 一次 git 提交，`git log --oneline` 应与本表对得上号」——
当场破功，**全程零告警**。

**根因**：规则一测量的是**在场**（`CHANGE-LOG.md` 有没有进暂存区），不是**内容**（记录有没有多一条）。
它挡得住「忘了写日志」，挡不住「写坏了日志」。

**修法**：加规则一之二——`CHANGE-LOG.md` 的暂存 diff 里，**记录行必须净增加至少一行**。

```bash
git diff --cached -U0 -- CHANGE-LOG.md          # 记录行 = 首格是日期的表格行
# 新增记录行数 > 删除记录行数  → 放行；否则拒绝
```

🔴 用「**净增**」而不是「有没有加号行」是关键：改写旧行在 diff 里同样是一个加号行（一加一减）。
只看有没有加号行，这个 bug 一个字都挡不住。

**教训**：

🔴 **一道闸门只保证它真正测量的那个量。**
「文件在暂存区里」和「日志多了一条记录」是**两个不同的量**，前者完全可以在后者不成立时为真。

写闸门的正确顺序是：先把「我要保住的不变量」写成一句**可数**的话——这里是
**「提交条数 = 记录行数」**——再检查闸门测的到底是不是那个数。

还有一层，比 bug 本身更值钱：**打穿它的不是恶意，是一个尽职的会话用 Edit 工具的自然结果。**
能被正常操作自然打穿的闸门，一定会被打穿，只是时间问题。

自测也照不变量来（已加进 [`00-架构规范.md`](00-架构规范.md) §9）：

```bash
git log --oneline | wc -l ; grep -cE '^\| [0-9]{4}-' CHANGE-LOG.md   # 两个数字必须相等
```

## L8 · 🔴 文档里一处陈述不同步，会同时误导多个互不相通的会话

**症状一（乐观陈述）**：成品 `docs/00-项目说明.md` §4 写着
「改 `projects/` 下的东西……`boundary-guard.sh` 会拦」，
而**同一份成品**的 `CLAUDE.md` / `README.md` / `.claude/rules/boundary.md` §4 三处都已如实写明
**这个方向拦不住**（L6）。

模拟测试里**两个互不相通的独立会话**都在这一句上绊了一下：一个自行把它订正了，另一个照着信了一会儿。
根因很朴素：L6 那轮改了「四处表述」，**漏了这一处**。

**症状二（衔接断裂）**：使用指南 §4.1 让把 `projects/` 下四个 demo **全删光**，
而宪法「新建子项目七步」第 2 步要求「**复制一个同类型的现有子项目**」——
删光之后建第一个子项目**无源可复制**。实测那个会话只能停下来，向外部要模具的路径才推得动。

两份文档**各自都自洽**，接起来断了。

**教训**：

🔴 **乐观方向的错误陈述最贵。** 说「有机器在管」而其实没有，读的人会**停止人工审阅**（同 D4）。
反过来，保守方向的错误（说没兜底其实有）只会让人多看一眼，代价小得多。

🔴 **文档之间的衔接处是没人检查的地方。** 单份文档自洽好查；
「A 文档让你删的东西，正好是 B 文档让你用的东西」这种洞，
只有把两份文档当成**一条连续的流程真的走一遍**才会暴露。
所以这类洞的检出方式不是审阅，是**让一个什么都不知道的会话照着文档从头做一遍**——
本轮的两个洞都是这么冒出来的。

**现状处理（两条纪律）**：

1. 改一条口径时，**先 `grep` 全仓库**找出所有提到它的地方，**一处改处处改**。
   本体系钩子有 7 份拷贝、规矩有 7 份拷贝（D1 的既有代价），文字口径同理。
2. 本次改的两处：成品 `docs/00-项目说明.md` §4 改成如实表述（含「靠纪律 + 子项目 git 历史事后可审计」）；
   指南 §4.1 与两份父项目宪法的「复制源」改成互相咬得上的说法——
   **复制源查找顺序**（先找项目内同类型，再找当初的模具）+ **模具位置写进立项那条 CHANGE-LOG 记录**。

## L9 · 🔴 `subtree add` 接进来的历史「在路径过滤下失明」；而做路径改写的 `sed` 会被 kebab-case 路径撑破

（2026-08-25 单仓迁移，D11）

**症状一**：用 `git subtree add` 把子仓库接进来，历史**看着**在里面，
但 `git log -- <那个子树路径>` **看不见那些提交**。后果直接命中本体系的命根子：
按单元核对账本（「该单元的非 merge 提交数 = 该单元 `CHANGE-LOG.md` 的记录行数」）**算不出来**，
`git log --follow` 一类的追溯也断在接入点。

**根因**：`subtree add` 接进来的历史里，**提交对象记录的路径还是子仓库里的原始路径**
（`README.md`、`docs/…`），不是它在新仓库里的位置（`projects/<单元>/README.md`）。
路径过滤按提交里的路径匹配，自然一条都匹配不上。

**修法**：**先路径改写，再合并。** 每个子仓库先用 `filter-branch` 把历史里的路径整体挪到
它在本仓的位置，再 `merge --allow-unrelated-histories` 接进来。
改写之后 `git log -- <单元路径>` 一条不落，账本核对得回来。

**症状二（藏在修法里的坑）**：路径改写的脚本里用 `sed` 拼替换表达式时，
用了 `-` 当分隔符——而本体系的目录名全是 **kebab-case**（`main-sub-architecture-project-demo`、
`demo-code-project`），路径里**本来就全是 `-`**，表达式当场被撑破。

🔴 **而它失败得一声不吭**：改写「成功」了，只是有一部分路径没被加上前缀。
不主动去看，你会以为迁移干净地做完了。

**修法**：分隔符换成路径里不可能出现的字符；**更要紧的是加断言**——
改写完之后逐条检查「这棵树里所有路径**都**带上了目标前缀」，不带就当场停。

**教训**：

🔴 **对历史做的批量改写，必须有一条改写后的断言，而且断言要针对「全部」而不是「抽样」。**
改写工具（`filter-branch` / `sed` / 路径重写）的共同性质是：**部分失败不报错**。
和 L5、L7 是同一族——**闸门只保证它真正测量的那个量**，
而这里如果你只「看了几条提交觉得对」，测量的其实是你的心情。

🔴 **符号选择也是一个正确性问题。** 分隔符、转义、引号这类「格式细节」在本体系里踩到第二次了
（第一次是 L1 的 `core.quotepath`）：命名约定（kebab-case、中文文件名）与工具默认行为撞车时，
撞出来的从来不是报错，是**静默走偏**。

## L10 · 局限：嵌套的 `.gitignore` 会挡下新文件——**报错还是静默，取决于你怎么写 `git add`**

（2026-08-25 单仓迁移，D11；失效形态 2026-08-25 验收实测订正）

**局限**：本仓库跟踪 `projects/` 下的模具与 demo（D11 展馆模式），
但**模具自己**和 `demo-parent-project` 自己的 `.gitignore` 里都写着 `projects/`。
于是在本仓库里碰那两棵子树时，`git add` 有**三种**表现，实测如下：

| 情形 | 输出 | 退出码 | 进暂存区了吗 |
|---|---|---|---|
| **(A)** 用**显式文件路径** add 一个被忽略的**新**文件 | 打印 `The following paths are ignored by one of your .gitignore files` + `hint: Use -f ...` | **1** | ❌ 没有 |
| **(B)** 用**宽泛 pathspec**（如 `git add projects/`）扫到那些新文件 | 🔴 **零输出** | **0** | ❌ 没有 |
| **(C)** add 一个 `projects/` 下**已被跟踪**的文件 | 照样打印 (A) 那段忽略警告 | **1** | ✅ **加进去了** |

```bash
# (A) 会喊：显式路径 + 新文件 → 报错 + 退出码 1 + 没加进去
git add projects/main-sub-architecture-project-demo/projects/<某个 demo>/新文件.md

# (B) 🔴 这才是真正的静默失效：宽泛 pathspec → 零输出、退出码 0、一个字节都没加
git add projects/
```

🔴 **别把 (A) 当成这个坑的形状。** (A) 是会喊的；**(B) 才是不报错的失效**。
所以正确的防法不是「小心看报错」，是**不要用宽泛 pathspec**——
本体系的提交纪律本来就要求显式路径（根 [`../CLAUDE.md`](../CLAUDE.md)「提交」一节），
那条纪律在这里正好把 (B) 兜住了：只写显式路径，失效就一定会喊。

🔴 **(C) 带一个额外的摩擦，实测踩过**：已跟踪文件**能**正常暂存，
但 git 仍然把那段忽略警告打出来并**返回退出码 1**。后果是——

```bash
git add <projects/ 下某个已跟踪文件> && git commit -m "..."   # ❌ 在本仓里不要这么写
```

`&&` 会因为那个 1 而短路，**`commit` 根本没执行**，而你看到的只有一段「ignored」警告，
很容易误判成「暂存失败」去反复重试。**在本仓里 `add` 与 `commit` 分两行写**，
暂存到底成没成以 `git diff --cached --name-only` 为准，**不看 `add` 的退出码**。

**为什么不修（不能把那行删掉）**：

| 备选修法 | 否掉的理由 |
|---|---|
| 删掉模具与 `demo-parent-project` 的 `.gitignore` 里那行 `projects/` | 🔴 **那是它们的出厂形态**。模具要教给真实项目的正是「父仓库排除整个 `projects/`」（D1），删了就等于把教材改错。模具会被复制几十次，**改坏一行教材，错的是几十个项目** |
| 把它们的 `projects/` 改成更细的规则（只排除某些东西） | 同上，还是改教材；而且规则一复杂，读者更学不明白 |
| 本仓不跟踪那些子树 | 那就没有展馆了，D11 的全部收益都没了 |

**现状处理（一条命令 + 两个习惯）**：

- 往那两棵子树新增文件时**显式强制**：`git add -f <路径>`。
- **只写显式路径，`add` 与 `commit` 分两行**——前半句让 (B) 无从发生，后半句让 (C) 咬不到人。
- 定期跑一条**全树漏网检查**（在仓库根跑，正常应输出 `CLEAN`）：

```bash
out=$(git ls-files --others --ignored --exclude-standard -- projects/ \
      | grep -vE '__pycache__|\.pytest_cache/')
[ -z "$out" ] && echo "CLEAN: 没有漏网文件" || printf '%s\n' "$out"
```

🔴 想看清输出里的中文路径，给 `ls-files` 加上 `-c core.quotepath=false`——
**同一个坑的第三次**（第一次 L1、第二次是 `init-repos.sh` 里给展品补 `git add -f` 时
被转义路径顶回来的 `did not match any files`）。

[`../scripts/init-repos.sh`](../scripts/init-repos.sh) 里对这条做了机器兜底：
首次提交前**只**force-add 那些「被 `projects/` 这条规则挡住」的文件
（用 `git check-ignore -v` 判断是哪条规则挡的，不无脑 `git add -f projects`，
否则会把各 demo 自己**合法**忽略的 `__pycache__` / `.pytest_cache` 一起提进去），
然后**断言 7 个单元的 `CLAUDE.md` 全部进了索引**，少一个就拒绝提交。

**教训一**：🔴 **「同一份文件既是教材又是配置」时，教材优先，配置的代价自己扛。**
`.gitignore` 在这里两个身份都有：对读者它是教材，对本仓它是会吞文件的配置。
本体系选择让教材保持正确，把代价（要记得 `-f`）用命令与断言接住。

**教训二（本条最初就写反了，2026-08-25 验收实测订正）**：
🔴 **写「某某会静默失效」之前，先跑一遍看它到底喊不喊。**
本条初稿断言「显式路径 add 新文件 → 什么都没发生，没有报错」，实测是**报错 + 退出码 1**；
真正零输出的是宽泛 pathspec 那种，而初稿连提都没提。
这属于 D4 那一族——**把会喊的写成不会喊，读者就会去防一个不存在的形状，
同时对真正沉默的那种毫无防备**。判据很硬：**失效形态是可执行、可复现的事实，不许凭印象写。**

## L11 · 🔴 出口安检的黑名单**对 git 历史零覆盖**——所以源头历史永不出境

（2026-08-25 单仓迁移，D11）

**局限**：[`03-发布与同步.md`](03-发布与同步.md) §2 的出口安检是一条 `grep -rn ... --exclude-dir=.git`。
那个 `--exclude-dir=.git` 是**必须**的（不排掉就是满屏二进制对象噪音），
但它带来一个必须说清的后果：

> **安检扫的是工作区，一个字都没扫 git 历史。**

而历史里**确实有**今天工作区里已经不存在的东西：

| 历史里有，工作区里没有 | 说明 |
|---|---|
| **脱敏之前的文本内容** | 本仓的 CHANGE-LOG 里明写过一次这类订正（把正文里的某个东西删掉）——**删掉的那一版仍然完整地躺在历史里** |
| **真实的提交身份** | 作者名与邮箱写在**每一条 commit 对象**里，不在任何工作区文件里，`grep` 天然照不到 |

🔴 **本文不写出具体是哪些值。** 写出来本身就是又一次泄漏——
这正是 CHANGE-LOG 里那条教训的形状：**记「我移除了 X」的时候不要在记录里写出 X**。

**所以定死一条铁律（不是建议）**：

> **源头的 git 历史永不直接 push 到公开仓库。公开仓库永远走快照制。**

不许 `git remote add` 然后 push，不许 `filter-branch` 洗一遍再推，
不许 `subtree split` 把某个单元的历史推上去。**一次都不许。**
已经写进 [`03-发布与同步.md`](03-发布与同步.md) §1（铁律）、§4（验证清单）、§5（已知不做的事）三处。

⚠️ **单仓之后这条更容易被误解**：以前不推历史有个「技术借口」——
7 个嵌套仓库压平后本来也推不上去。现在源头**就是一个仓库**，
「直接推上去不就完了」看起来顺理成章，**而它恰好是错的**。
借口没了，规矩得自己立住。

**教训**：

🔴 **一道安检的覆盖面，等于它实际扫过的字节，不等于你以为它保护的范围。**
「发布前扫一遍全仓库」听着是全覆盖，其实排除了整个 `.git`——
而 `.git` 里装着这个仓库**曾经**的每一个版本。

🔴 **删除不等于删除。** 在版本控制里，「把敏感内容从文件里删掉并提交」这个动作
只改变了**当前**版本；历史是不可变的，那份内容仍然可读。
真要根除得重写历史（而重写历史又会撞上 L9 那一族的坑），
所以本体系选的是更便宜也更可靠的一条：**让历史根本不出境。**

# 三、真实会话模拟测试验到了什么（2026-08-19）

方法：在一个复制出来的模拟项目里跑真实无头会话（`claude -p`），每个场景后用文件系统 / git 状态做客观断言，
关键机制另做机械验证（直接喂 JSON 给钩子、直接构造提交）。8 个会话。
被测的模板**全程一字未改**（前后指纹一致）。

之后又**补跑 2 轮**，专测「在父项目会话里跨子项目干活，提交还成不成立」（下表标 ★ 的行）。

**成立的设计**（这些不是推测，是验到的）：

| 设计 | 验到的证据 |
|---|---|
| **确立仪式的触发机关**（D3） | 「复制改名 → 状态自动变脏 → 仪式自动触发」在**两层**上都验到；全新会话主动发起仪式、问了 5 个问题、**没擅自替人签确认**（状态文件字节未变）。不需要任何重置脚本 |
| **仪式是钩子推的，不是靠 agent 自觉** | 抓会话初始上下文，`SessionStart` 钩子的原文出现在流里——即仪式不依赖 agent 读 `CLAUDE.md` 自己推断 |
| 🔴 **局限如实写出来**（D4） | **最重要的一条证据**：四个独立会话在没有任何提示的情况下，都主动说出了体系自己声明的局限（第 7 步无钩子兜底 / 父改子拦不住 / Bash 能绕过 Write 钩子）。**把局限写进钩子注释和规矩正文，agent 真的会读到并转述给用户**——D4 那句「假的安全感比没有安全感更危险」有了正面反证 |
| **提交硬闸的教育效果** | 有个会话**一次就带齐了三件套**（改的文件 + CHANGE-LOG + README），根本没撞闸——说明宪法里写清规矩比撞一次闸更有效 |
| **中文路径的 quotepath 修复**（L1） | 拒绝信息里中文文件名正常显示，前缀匹配正常触发 |
| **越界判定不因路径写法被绕过** | macOS 的 `/tmp` → `/private/tmp` 符号链接被 `pwd -P` 正确吸收，写法不同不改变判定 |
| **父项目第 7 步靠纪律，现阶段够用**（L3） | 那一步没有任何机器兜底，实测 agent **守住了**：父 README 索引加了行、父 CHANGE-LOG 记了「新增子项目」、并在父项目单独提交 |
| ★ **跨子项目干活时提交完全成立，钩子按仓库各自生效**（§4 git 约定 / D1） | 明确授权的那一轮会话在**父项目会话里**改了子项目和父项目，**分两次提交进两个仓库**：子仓库那次带了**它自己的** `CHANGE-LOG.md` 净增 1 行（记录行 +1/−0），父仓库那次只含父级文件（`projects/` 下 **0 个文件**）；两个仓库事后都干净。两轮会话全程**无 `--no-verify`、无 `git add -A`**（流里 0 次）。它还自己写了 `.claude/cross-edit-allow` 放行条、改完删掉 |
| ★ **「父根 `git status` 看不见子项目的脏」是真的**（机械验证） | 手工把子项目 README 改脏后：子仓库 `git status --short` 显示 `M README.md`，而**父根 `git status` 输出「nothing to commit, working tree clean」**。指南 §8.2 的全树扫描命令准确点出 `./projects/my-sub-tool`，还原后再跑无输出 |

**验到是软的**（要知道，别当铁桶）：

| 项 | 事实 |
|---|---|
| 确立仪式是**软闸** | 它是「注入上下文的指示」，不是强制。探针会话给一句「只回答两个字：收到」，agent 就先服从用户、把仪式放在一边。这与指南 §3「直说跳过，agent 会照办」一致，属设计内——但**硬的只有 `pre-commit` 那一道** |
| 越界拦截**常常不是它在起作用** | 有个会话是**读了钩子源码后自己停下的**，钩子根本没被触发。所以「会话没越界」不等于「钩子有效」，机械验证是必要的补充 |
| ★ 不带授权时，「父会话跨子项目干活」**会被 agent 一口回绝，活只干一半** | 第一轮的提示是「改子项目 README + 改父项目文档 + 都提交好」，会话**只做了父项目那半**就停了，理由引的是宪法「边界」那条和 L6（父改子拦不住、要改就去子项目开会话）。机制没问题，是**文字缺口**：三份文档只写了「不该在父会话里改子项目」，没写「主人明确要求时该怎么做」。已补：`01-使用指南.md` §8 + 成品根与 `demo-parent-project` 两份宪法里的精炼版（含「主人明确要求就照办」） |

## 附：翻案怎么翻

以上任何一条都可以推翻。要求只有两个：

1. **在本文里改**，不要只在会话里说——不写下来的翻案，下一个 agent 读不到。
2. **说清你重新论证了哪一条「否掉的替代」**。每条决策都列了否掉的方案和理由，
   翻案就是证明那个理由不再成立（或者一开始就错了）。

翻案后记得：**规范（`00`）和使用指南（`01`）要同步改，模板成品也要同步改**。

🔴 **同步的做法随 D11 变了**：模具现在与本仓同处一个仓库，可以直接改、
甚至和规范放在**同一次提交**里原子完成（这正是 D11 换来的好处之一），
不用再换目录开会话、也不用走跨项目授权流程。
换来的约束是提交硬闸 v2 会**按单元查账**：动了哪个单元，就要在**那个单元自己的**
`CHANGE-LOG.md` 里净增一行——拿仓库根的日志顶包不算数。
