# 00 · 「总项目 - 多子项目」架构规范

> 本体系的完整规范。新开会话的 agent 读完本文 + 根 `README.md`，就能独立按规矩干活。
> 本文是**规范**（该怎么做）；**怎么用模板开新项目**见 [`01-使用指南.md`](01-使用指南.md)；
> **当初为什么这么定**见 [`02-设计决策.md`](02-设计决策.md)。
> 具体到某个项目的规矩在该项目的 `CLAUDE.md`（项目根）与 `.claude/rules/`。

## 0. 这套架构为了什么（立法意图）

先说目的，再看目录结构——不然目录只是一堆约定，没人知道为什么要照着摆。

**这套架构是用来「拆」的**：把一个大到没法一口吃下的目标，拆成一棵能一直往下长的树。
下面这段是项目主人 2026-08-19 的原话，也是本节的立法依据：

> 「我这么设计项目的架构，就是为了『拆分』我的一个大项目，通过不断的调研，
> 可能在实验、调研文档的支撑下会拆分出很多的尝试性方向，**这些尝试可能最终放弃，但是还是要留档**——
> 同时这个父子架构可以理解为**对任务的拆解**……
> **我不希望他们一个一个项目毫无联系散落在各处。**」

拆成四条意图，每条都对应后面的具体约定：

| # | 意图 | 大白话 | 落在哪 |
|---|---|---|---|
| 1 | **目录树 = 任务拆解树** | 一个大需求必然拆成小任务，小任务还能再拆。父项目管秩序，子项目干活，子项目自己又能当父项目，**层数没有上限** | §1 递归性 · §2.4 父项目范式 |
| 2 | **调研会不断催生新方向** | 调研 / 实验做着做着就冒出「这条路值得单独试一下」。每个值得试的方向就在树上开一个子项目去试 | §2.5 何时拆子项目 |
| 3 | **尝试可以死，档案必须留** | 放弃的方向是**资产不是垃圾**——它至少证明了「这条路不通」。所以放弃的子项目不删目录、不移出树，只改状态 + 写放弃说明 | §2.4 生命周期状态 |
| 4 | **所有尝试长在同一棵树上** | 每个节点都写明自己因什么而生，彼此有来由可查，不散落在各处 | §2.4 索引表的「状态」列 · §5 来由 |

真实例子就是本体系被造出来的那条链：

```
给 PM 提效（大目标）
  └─ 多轮调研后想出「工作台」这个模式
       └─ 工作台里要加「商品指纹」
            └─ 于是又要为商品指纹做一轮调研
```

每一步都是上一步的产物催生出来的，**每一步都该是树上的一个节点，而不是桌面上又一个孤立文件夹。**

🔴 **推论（后面所有约定都是从这四条推出来的）**：
一个项目最要紧的两条元信息是**它现在处于什么状态**（活着 / 停了 / 完了 / 放弃了）
和**它因什么而生**（来由）。缺了前者，树上全是看不出死活的节点；
缺了后者，半年后没人知道这个目录为什么存在——两样都缺，就退化成「毫无联系散落各处」。

## 1. 体系长什么样

```
<总项目>/                       ← 父项目，自己是一个 git 仓库
├── CLAUDE.md                   🔴 项目宪法（在项目根，不在 .claude/ 里）
├── .claude/
│   ├── HARNESS-STATUS.md       确立状态
│   ├── rules/                  逐条可执行的规矩
│   ├── hooks/                  Claude Code 钩子
│   └── settings.json           把钩子挂上
├── .githooks/pre-commit        提交硬闸
├── README.md                   接口文档 + 子项目索引表
├── CHANGE-LOG.md               父项目自己的历史
├── docs/                       统筹类文档
└── projects/                   ← 被父仓库 .gitignore 排除
    ├── <子项目 A>/             各自是一个独立完整的 git 仓库
    ├── <子项目 B>/
    └── <子项目 C>/             ← 子项目本身也可以是父项目，无限递归
        └── projects/
            └── <孙项目>/
```

**递归性是本体系的核心**：父项目和子项目用的是**同一套骨架**。
一个项目是「父」还是「子」，只取决于它有没有 `projects/` 目录，不是两种不同的东西。

> 本项目（`agent-project-scaffold`）自己就是这个结构的实例：
> 它是父项目，`projects/main-sub-architecture-project-demo/` 是它的子项目，
> 而那个子项目自己又是父项目、下面还挂着四个 demo 和一个孙项目。

### 1.1 🔴 宪法放**项目根的 `CLAUDE.md`**，不放 `.claude/CLAUDE.md`

**约定（已实测定案）**：每个项目的宪法一律是 `<项目根>/CLAUDE.md`。
`.claude/` 目录里只放四样：`HARNESS-STATUS.md` / `rules/` / `hooks/` / `settings.json`。

理由：

| 理由 | 说明 |
|---|---|
| **标准位置** | 项目根的 `CLAUDE.md` 是 Claude Code 官方文档**首要列出**的项目级位置，被长期承诺 |
| **兼容性最好** | 各版本、各衍生工具（以及其它读 `CLAUDE.md` 的 agent 工具链）都认根目录这一份 |
| **不赌未来** | `.claude/CLAUDE.md` 当前版本**实测确实也生效**，但它没有同等的书面承诺。模板是要长期复用、被复制几十次的东西，不能押在一个可能变的行为上 |

🔴 **绝对不许两处同时存在 `CLAUDE.md`**。两份都会被加载 → 同一套指令进两遍上下文，
既浪费 token，又会在两份内容不同步时产生自相矛盾的指令（Claude 可能任选其一执行）。
**要挪就用 `git mv` 移动，不要复制。**

自检：`ls CLAUDE.md .claude/CLAUDE.md` 应当只有前者存在。

取舍全文见 [`02-设计决策.md`](02-设计决策.md) D2。

### 1.2 🔴 状态行必须写成**锚定行**

`.claude/HARNESS-STATUS.md` 的当前状态**必须**是独占一行的二级标题，二选一，一字不差：

```markdown
## 当前状态：已确立
## 当前状态：未确立
```

同一份文件里还必须有这一行（钩子按前缀解析，项目名要**精确等于目录名**）：

```markdown
- 项目名：<当前目录名>
```

**为什么强制成锚定行**：`harness-check.sh` 判定「未确立」时匹配的是 `^## 当前状态：未确立`——
**行首锚定 + 完整前缀**，而不是在全文里找「未确立」三个字。

这一条是踩坑改出来的。早期版本用的是全文 `grep -q "未确立"`，结果状态文件里正常的
**说明性散文**（比如「两者对不上 → 自动触发确立仪式」「否则会被判定为**未确立**」）
含有这三个字，于是一个明明已确立的项目每次开会话都被判成未确立，噪音天天有。

推论，两条都要遵守：

1. **状态行只许出现在那一个位置**，不许在文档别处再写一次 `## 当前状态：…`。
2. 状态文件里的散文**可以随便提「未确立」**——只要不写成行首的 `## 当前状态：未确立` 就不会误触发。

教训的完整版见 [`02-设计决策.md`](02-设计决策.md) L2。

## 2. 四类项目 · 定义与范式

选型判据用一句话就能定：**你最终要交付的那个东西，长什么样？**

| 类型 | 交付物 | 一句话判据 | 样板 demo |
|---|---|---|---|
| **代码项目** | 能跑起来的应用 / 库 / 工具 | 「做完之后有个东西能运行」 | `demo-code-project` |
| **实验项目** | 一个经过验证的方案 / 结论 | 「做完之后知道该选哪条路」 | `demo-experiment-project` |
| **文档仓库** | 可被反复引用的知识 | 「做完之后有份东西以后要一直翻」 | `demo-docs-project` |
| **父项目** | 秩序（分工 / 索引 / 规矩） | 「它自己不产出内容，它管着一堆产出内容的」 | `demo-parent-project` |

四个 demo 都在 [`../projects/main-sub-architecture-project-demo/projects/`](../projects/main-sub-architecture-project-demo/projects) 下。
选型的实操版（含判不准时怎么办）见 [`01-使用指南.md`](01-使用指南.md) §2。

判不准时的兜底规则：

- 又要写代码又要做实验 → 看**代码是不是交付物**。代码只是为了得出结论 → 实验项目。
- 又要写文档又要写代码 → 看**文档是不是给别人反复查的**。只是自己项目的说明 → 代码项目里的 `docs/`。
- 一开始判错不致命：四类的骨架是同一套，改的只是 `CLAUDE.md` 里的范式段落。

### 2.1 代码项目范式

| 项 | 规矩 |
|---|---|
| 测试 | **测试是提交准入**。没有测试的功能不成立 |
| 分支 | 一功能一分支，做完即合即删 |
| 目录 | `src/` 源码（按职责分模块，不堆单文件）· `tests/` 测试 · `docs/` 需求与设计 |
| 交付说明 | 每次交付必答三问：**怎么起 / 点哪里 / 该看到什么** |
| 文档 | `docs/01-需求.md`（目标 / 功能清单 / 边界）· `docs/02-设计.md`（架构 / 关键取舍） |

### 2.2 实验项目范式

| 项 | 规矩 |
|---|---|
| 核心资产 | `EXPERIMENTS.md`，**只增不改**——写过的轮次不许回头修改 |
| 每轮四要素 | **假设 / 做法 / 数字 / 判定**，缺一不算一轮 |
| 负面结论 | **也是资产**。「A 不行」和「B 行」一样值钱，必须留档 |
| 花钱 | 调付费接口 / 大规模跑数**前**必须报预算，等确认 |
| 目录 | `experiments/` 脚本 · `experiments/data/` 样例数据 · `docs/` 痛点 / 决策 / 待决策 / 结论 |

### 2.3 文档仓库范式

| 项 | 规矩 |
|---|---|
| 入口 | 新材料**先进 `inbox/`**，不直接进 `archive/` |
| 归档 | 定期把 `inbox/` 的东西整理、编号、移入 `archive/` |
| 标注 | 每份材料头部必须有**来源 / 日期 / 可信度** |
| 索引 | `README.md` **必须索引全部内容**，一份材料一行 |
| 不做 | 不在这里写代码、不在这里做决策——文档仓库只沉淀知识 |

### 2.4 父项目范式

要点：**交付物是秩序**；父级日志只记父级；不跨界改子项目；
父项目根目录不堆业务文件，业务内容一律在 `projects/` 下的子项目里。

样板见 `demo-parent-project` 的 `CLAUDE.md`，以及本项目自己的 [`../CLAUDE.md`](../CLAUDE.md)。

#### 🔴 子项目生命周期状态（父项目 README 索引表必须有这一列）

| 状态 | 含义 | 什么时候用 |
|---|---|---|
| 🚧 进行中 | 正在推进 | 默认状态 |
| ⏸ 暂停 | 有意搁置，还打算回来 | 被别的事挤掉了优先级 |
| ✅ 已完成 | 交付物已交出，不再主动推进 | 代码上线 / 结论定稿 |
| 🗄 已放弃（留档） | 决定不做了，只留档案 | 方向被否 / 前提变了 / 验证出这条路不通 |

🔴 **这四个值就是父项目 `README.md` 子项目索引表「状态」列的全部取值。**
不要往这一列写「能不能跑」「几个测试绿」——那些是运行情况，写进「是什么」列。
**状态列答的是生命周期：这个节点还活着吗。**

一个特例要知道：文档仓库里的材料**永不归档也是正常结局**（一份便签的结论是「不改」，
它就永远待在 `inbox/`）。这不影响项目本身的状态——只要还在收材料，项目就是 🚧 进行中。

#### 🔴 铁律：放弃的子项目不删目录、不移出树

**「决定不做」本身是信息。** 放弃一个方向时最该留下的恰恰是「为什么不做」——
半年后有人想起同一个主意，这份档案能省下他重走一遍的时间（立法意图见 §0 第 3 条）。

放弃时**只做两件事，一件都不许少**：

| # | 做什么 | 在哪做 |
|---|---|---|
| 1 | 父项目 `README.md` 索引表里，把这一行的状态改成 🗄 已放弃（留档） | 父项目，记一条父级 CHANGE-LOG |
| 2 | 子项目 `README.md` **顶部**加一段「放弃说明」 | 子项目自己，记它自己的一条 CHANGE-LOG |

放弃说明三句话，缺一不算：

```markdown
> **🗄 放弃说明（YYYY-MM-DD）**
> **为什么停**：……
> **验证到哪**：已经确认了什么、还有什么没验
> **若重启从哪接**：下一个人接手该从哪个文件 / 哪一步开始
```

不许做的三件事：**删目录**、**把目录移出 `projects/`**、**清掉它 CHANGE-LOG 里的历史**。
🔴 删掉的档案等于这次尝试没发生过——下一个人（或者半年后的你自己）会把同一条死路重走一遍。

### 2.5 什么时候把一件事拆成子项目

**判据三条，占两条就值得拆**：

| # | 判据 | 换句话说 |
|---|---|---|
| 1 | 它有**自己的交付物**和自己的生命周期 | 它能独立地「做完」，也能独立地「做不完」 |
| 2 | 它**可能被单独放弃** | 放弃它，父项目照样能往下走 |
| 3 | 它需要**独立的档案和历史** | 以后要单独翻它做过什么、为什么这么选 |

反例——下面这些**不该拆**，它们是整理问题，不是拆分问题：

| 情形 | 该怎么办 |
|---|---|
| 它只是父项目的一个章节 / 一份文档 | 写进父项目的 `docs/`，不开新仓库 |
| 只是文件多了、目录深了 | 整理目录 |
| 只是想给一段代码换个位置 | 那是重构 |

**每个子项目都有固定成本**：一套 harness、一份 README、一条独立历史、一次确立仪式。
成本值不值，就看上面三条占了几条。

#### 🔴 调研 → 拆分的闭环（§0 意图 ②③ 的落地路径）

实验项目和文档仓库都会产出「导出的新方向」。它被采纳时的**标准动作**是这条链：

```
某份调研 / 某轮实验得出「这条路值得单独试」
      ↓
按宪法「新建子项目七步」开一个新子项目
      ↓
第 7 步在父项目 CHANGE-LOG 那条记录里写明来由：因哪份调研 / 哪条实验结论而建
      ↓
父项目 README 索引表加一行：状态 🚧 进行中，「是什么」列带上来由
      ↓
试通了 → ✅ 已完成 ／ 试不通 → 🗄 已放弃（留档）+ 放弃说明
```

**两头都不许断**：往前要能查到「它因什么而生」，往后要能查到「它是怎么结束的」。
这就是 §0 第 4 条说的「所有尝试长在同一棵树上」——树上每个节点都有来由，也都有结局。

## 3. 目录与命名约定

| 对象 | 约定 | 例 |
|---|---|---|
| 目录名 | **英文小写 kebab-case** | `demo-code-project` / `experiments` |
| Python 包目录 | 下划线（语言限制，例外） | `src/unit_converter` |
| 文档文件名 | **中文**，带数字编号前缀 | `docs/01-需求.md` |
| 根级固定文件 | 全大写英文 | `README.md` / `CHANGE-LOG.md` / `CLAUDE.md` / `EXPERIMENTS.md` |
| 编号 | `00-` 留给总纲；表达**阅读顺序**不是创建顺序 | `00-架构规范.md` |

🔴 **编号一旦定下不要重排**（别处引用会全部失效）。要插在中间用 `01b-`。

🔴 **全仓库不许出现绝对路径**。文档里引用别处一律写相对路径；
脚本里用 `$CLAUDE_PROJECT_DIR` 或 `git rev-parse --show-toplevel`。
理由：换机器、改目录名、复制模板，绝对路径一律当场失效。

## 4. git 约定：独立嵌套仓库

**已拍板：每个项目自己 `git init` 一个完整仓库，父仓库 `.gitignore` 忽略整个 `projects/`。**

否掉 submodule / subtree / 单一大仓库的完整理由见 [`02-设计决策.md`](02-设计决策.md) D1。
一句话版本：**submodule 要在父仓库存子仓库的 commit 指针，这与「父级日志只记父级」直接冲突**——
每次子项目提交都得回父仓库更新一次指针，而那次更新在父项目的 CHANGE-LOG 里根本写不出一条有意义的记录。

### 每个仓库都要做的初始化

```bash
git init -b main
git config core.hooksPath .githooks     # 🔴 启用提交硬闸，每个仓库各做一次
git add <显式路径>
git commit
```

🔴 **`git config core.hooksPath .githooks` 是每仓库一次的手工动作，clone 下来也要重做**——
git 不会自动启用仓库内的钩子（这是 git 的安全设计）。忘了这步，提交硬闸静默失效。
自检：`git config --get core.hooksPath` 应该输出 `.githooks`。

### 提交纪律

- 用 `git add <显式路径>`，**不用 `-A` / `.`**。
- **一条 CHANGE-LOG 记录 = 一次 git 提交**，`git log --oneline` 与 `CHANGE-LOG.md` 应能对上号。
- 🔴 **一次会话动了几个仓库，就要做几次提交**（各仓库各自暂存自己的 `CHANGE-LOG.md`）。
  尤其注意：**父仓库的 `git status` 看不见子项目的脏改动**，别拿它当「全都提交完了」的凭据。
  跨子项目干活的提交做法与全树扫描命令见 [`01-使用指南.md`](01-使用指南.md) §8。

## 5. README 与 CHANGE-LOG 的职责

完整规矩在各项目的 `.claude/rules/docs-discipline.md`。六句话摘要：

1. **README 答「现在有什么」，CHANGE-LOG 答「过去发生过什么」。**
2. **README 是写给 AI agent 的接口**——开头两三段自我介绍（我是谁 / 交付什么 / 怎么维护），
   主体是**完整索引表**，agent 靠它决定读哪个文件，而不是把整棵树读一遍。
3. **README 要对人也可读**：不堆缩写、不写只有作者看得懂的内部黑话。
4. **父级日志只记父级**：子项目的变化记在子项目自己的 CHANGE-LOG，不往上冒泡
   （子项目根本不在父仓库的提交范围内，硬记就是假历史）。
5. 🔴 **每个项目的自我介绍要写明「为什么存在 / 源自哪里」**（来由：因哪个需求 / 哪份调研 /
   哪条实验结论而建）。缺了这句，半年后没人知道这个目录为什么在这儿（§0 推论）。
6. 🔴 **父项目的子项目索引表必须有「状态」列**，取值是生命周期四态
   （🚧 进行中 · ⏸ 暂停 · ✅ 已完成 · 🗄 已放弃（留档）），见 §2.4。

## 6. 三个钩子

规矩的牙齿。**没有这三个，上面所有文字都只是呼吁。**

| # | 钩子 | 挂在哪 | 强制什么 |
|---|---|---|---|
| 1 | `.githooks/pre-commit` | git 提交前 | **按项目单元判定**：① 某单元改了任何东西，必须同时暂存**该单元的** `CHANGE-LOG.md`，**且它的暂存 diff 里记录行要净增至少一条**；② 该单元的 `docs/`/`projects/` 有新增/删除/改名，必须同时暂存**该单元的** `README.md` |
| 2 | `.claude/hooks/boundary-guard.sh` | Claude Code `PreToolUse` (`Write\|Edit`) | 目标文件不在本项目树内 → 退出码 2 阻止 |
| 3 | `.claude/hooks/harness-check.sh` | Claude Code `SessionStart` | harness 未确立 → 向上下文注入「先做确立仪式」的指令 |

### 6.1 pre-commit（提交硬闸，路径感知 v2）

- 🔴 **判定的单位是「项目单元」，不是整个仓库。**
  单元 = 从改动文件所在目录**向上找，最近的那个含 `CLAUDE.md` 的目录**；一路找到顶都没有就算仓库根。
  单元字典取自 **git 索引**（`git ls-files`）而不是工作区——本次新建的 `CLAUDE.md` 已经在索引里、
  本次删除的已经不在，**归属跟着「提交后的世界」走**，而不是跟着硬盘现状走。
  一次提交允许同时动多个单元（`git mv` 一个单元目录必然同时动到新旧两个，禁了就没法改名），
  但**每个被动到的单元都要各自补上自己的那行日志**。
- 🔴 **在本规范教的形态里，v2 与旧版逐条等价。** 本规范教的是「一个项目 = 一个仓库」
  （§4 独立嵌套仓库），这种仓库里只有根目录有 `CLAUDE.md`，所有文件都归仓库根这一个单元，
  两条规则的行为**一个字都没变**。v2 是为「一个仓库里并排装着多个项目单元」这种形态加的——
  那不是本规范教给项目的形态，取舍见 [`02-设计决策.md`](02-设计决策.md) D11。
- 🔴 **归属算不出来时是「拒绝」，不是「放行」**：暂存区明明有变更、内部归属表却是空的，
  说明钩子自己出了问题，此时直接拒绝并把变更清单打给你看。
  （理由与 D6 的 fail-open 不冲突：boundary-guard 解析失败最可能是「这次调用本来就不该拦」，
  而这里归属表为空**只可能是钩子坏了**，放行等于硬闸静悄悄形同虚设。）
- **没有跳过开关**。规则一触发就是拒绝，报错信息里按单元列出问题并给出可直接复制的补救命令。
- 🔴 **规则一之二：验的是「日志真的多了一条」，不是「日志文件在暂存区里」。**
  钩子看**该单元** `CHANGE-LOG.md` 的暂存 diff（`git diff --cached -U0 -- <单元根>/CHANGE-LOG.md`），
  要求**记录行净增加至少一行**（记录行 = 首格是日期 `YYYY-MM-DD` 的表格行，
  所以表头行和 `|---|` 分隔行天然不算）。
  **改写旧记录那一行不算**——diff 上是一加一减、净增 0，判拒。
  用「净增」而不是「有没有加号行」，正是因为改旧行同样会产生加号行。
  这条是实测事故补上的，来龙去脉见 [`02-设计决策.md`](02-设计决策.md) L7。
- 规则二只管**结构变化**（新增 / 删除 / 改名），不管内容改动——避免改个错别字也要动 README 的噪音。
- 首次提交天然通过（`CHANGE-LOG.md` 本来就在暂存区里）。
- 🔴 **必须带 `-c core.quotepath=false`**：git 默认把非 ASCII 路径转义成 `"docs/\346\236\266..."`，
  中文文件名会因为多出来的引号躲开 `^docs/` 前缀匹配。**本体系文档名一律用中文，所以这不是边角情况，是主路径。**
  详见 [`02-设计决策.md`](02-设计决策.md) L1。
- 🔴 **诚实说明**：git 的 `--no-verify` 仍可绕过，这是 git 自身设计，钩子内堵不死。
  它挡的是「忘记」，不是「蓄意」。
- 🔴 **局限**：规则二只覆盖 `docs/` 和 `projects/` 两个前缀（**相对单元根**算）。
  别的目录（`inbox/` `archive/` `src/`）的结构变化**不触发**，索引同步靠纪律。
  理由见 [`02-设计决策.md`](02-设计决策.md) L4。
- 🔴 **局限（v2 带来的）**：新建一个子单元时，它自己的 `CLAUDE.md` 跟着同一次提交进索引，
  于是那批文件**全部归新单元**，不会触发父单元的规则一 / 规则二。
  所以「新增子项目要更新父项目索引表」这一步在 v2 下**仍然没有机器兜底**（同 L3，靠纪律）。
  反方向（删除 / 改名一个子单元）则会：旧路径归回父单元并触发父单元的检查。

### 6.2 boundary-guard（越界拦截）

从 stdin 读 Claude Code 的钩子协议 JSON，取 `tool_input.file_path`，
解析成绝对真实路径后与项目根做前缀比较。解析优先 `jq`，其次 `python3`，最后正则兜底；
**都拿不到就放行**（钩子的职责是拦越界，不是给正常工作添堵；取舍见 [`02-设计决策.md`](02-设计决策.md) D6）。

放行口只有一个：`.claude/cross-edit-allow` 存在、修改时间在 **30 分钟**内、且某一行是目标路径的前缀。
授权流程见 `.claude/rules/boundary.md` §3。

🔴 **已知局限（写进规矩里了，不许当它是铁桶）**：

| 局限 | 说明 |
|---|---|
| Bash 绕得过去 | 只拦 `Write`/`Edit`。`cat >` / `sed -i` / `cp` 写文件，钩子看不见 |
| 不拦人工修改 | 人手动改文件不经过工具层 |
| 🔴 **拦不住「父项目改子项目」** | 子项目物理上就在父项目树**内**（`projects/<子项目>/`），钩子按「是否在树内」判定，所以这个方向**一律放行**。而这恰恰是本体系最常发生的越界方向——**纯靠纪律**，详见 [`02-设计决策.md`](02-设计决策.md) L6 |
| 解析失败时放行 | 刻意选择的 fail-open，见 [`02-设计决策.md`](02-设计决策.md) D6 |

靠纪律 + 人工审阅 diff + 对方仓库自己的提交硬闸兜底。

### 6.3 harness-check（确立仪式触发器）

判定「未确立」的三条：

| # | 条件 | 匹配方式 |
|---|---|---|
| 1 | `.claude/HARNESS-STATUS.md` 不存在 | 文件存在性 |
| 2 | 文件里有 `## 当前状态：未确立` | 🔴 **行首锚定**（`^## 当前状态：未确立`），不是全文找关键词 |
| 3 | 文件里 `- 项目名：` 记录的名字 **≠ 当前目录名** | 前缀解析 + 精确比较 |

第 2 条的锚定要求见 §1.2——早期版本全文 grep「未确立」，被状态文件自己的说明文字误触发。

🔴 **第 3 条是整套体系的关键机关**：

```
demo-code-project/     记录「demo-code-project」= 目录名 → 安静，零噪音
      ↓ 复制 + 改名
my-new-tool/           记录仍是「demo-code-project」≠ 目录名 → 自动触发仪式
```

**复制模板改名后仪式自动重新触发，不需要任何重置脚本，也不可能忘记重置。**
所以样板 demo 的 `HARNESS-STATUS.md` 都写成**已确立的示范样本**（各记自己的名字）——
它们在原地是安静的，一旦被复制改名就自动变回未确立。设计取舍见 [`02-设计决策.md`](02-设计决策.md) D3。

副作用（要知道）：给项目目录改名 = 重新触发一次仪式。这是可接受的，
目录改名通常意味着定位变了，重新对一次规矩本来就该做。

### 6.4 settings.json 怎么挂

```json
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Write|Edit",
        "hooks": [{ "type": "command",
                    "command": "bash \"$CLAUDE_PROJECT_DIR/.claude/hooks/boundary-guard.sh\"" }] }
    ],
    "SessionStart": [
      { "matcher": "startup|resume|clear",
        "hooks": [{ "type": "command",
                    "command": "bash \"$CLAUDE_PROJECT_DIR/.claude/hooks/harness-check.sh\"" }] }
    ]
  }
}
```

关键事实（据 Claude Code 官方 hooks 文档）：

- `PreToolUse` **退出码 2 = 阻止工具调用**，stderr 内容会给到 Claude。其它非零码只是报错，不阻止。
- `SessionStart` 的 **stdout 会作为上下文注入**给 Claude（这是少数几个有此待遇的事件之一）；
  它的退出码被忽略，所以 `harness-check.sh` 一律返回 0。
- `SessionStart` 支持的 matcher：`startup` / `resume` / `clear` / `compact` / `fork`。
  本模板挂 `startup|resume|clear`，**刻意不挂 `compact`**——压缩上下文时再刷一遍仪式指令是纯噪音。
- `$CLAUDE_PROJECT_DIR` 由 Claude Code 注入，指向项目根。**用它，不要写绝对路径。**

⚠️ **若钩子没生效，按这个顺序排查**：
① `.claude/settings.json` 的 `hooks` 语法是否正确（JSON 有没有多余逗号）；
② 当前 Claude Code 版本是否支持该事件与 matcher（版本较老时 `SessionStart` 可能不可用）；
③ 会话里执行 `/hooks` 查看当前生效的钩子集合；
④ 直接命令行调脚本自测（见 §9）；
⑤ 脚本有没有可执行位（`chmod +x`）——本模板用 `bash <脚本>` 调用，所以即使没有可执行位也能跑。

## 7. 跨项目授权流程

完整版在各项目 `.claude/rules/boundary.md` §3。四步：

1. **停下来问用户**——说清要改哪个项目的哪个文件、为什么、后果是什么。
2. **口头同意后写放行条** `.claude/cross-edit-allow`，每行一个路径前缀（30 分钟自动过期，不进 git）。
3. **改完提醒用户**：对方项目提交时会被对方的 `pre-commit` 硬闸要求补 `CHANGE-LOG.md`。
   🔴 **不要替对方项目提交，也不要跑去替对方改 CHANGE-LOG**——那本身又是一次越界。
4. **删掉放行条**（忘了也会自动过期）。

## 9. 钩子自测（不用开 Claude 会话）

🔴 **这几条命令必须真的敲进终端看输出，不许「读一遍觉得对」就当测过了。**
本体系已经因为这个吃过亏：自测清单第 1 条写着「应当被拒绝」，而它**从来没被拒绝过**
（规则一漏了 `README.md`，而用例恰好只测了这一个文件）。详见 [`02-设计决策.md`](02-设计决策.md) L5。

在**任意一个按本规范搭起来的项目根目录**下执行：

```bash
# 1. pre-commit 规则一 —— 没带日志，应当被拒绝
echo x >> README.md && git add README.md && git commit -m "test"

# 2. pre-commit 规则一之二 —— 只改旧记录那一行（净增 0），应当仍被拒绝
#    手工把 CHANGE-LOG 最上面那条记录的「改了什么」一格改几个字，然后：
git add CHANGE-LOG.md && git commit -m "test"

# 3. pre-commit —— 另起一行写本次记录后，应当通过
#    手工在表头下面新插一行 | YYYY-MM-DD | 自测 | 验证硬闸 |，然后：
git add CHANGE-LOG.md && git commit -m "test"

# 3b. 事后核对不变量：两个数字必须相等
#     （这条按「一个项目 = 一个仓库」写，也就是本规范教的形态。
#      若一个仓库里并排装着多个项目单元，要按单元逐个核对，命令见 02 的 D11）
git log --oneline | wc -l ; grep -cE '^\| [0-9]{4}-' CHANGE-LOG.md

# 4. boundary-guard —— 越界应输出拦截理由并 exit 2
echo '{"tool_name":"Write","tool_input":{"file_path":"/tmp/x.txt"}}' \
  | CLAUDE_PROJECT_DIR="$(pwd)" bash .claude/hooks/boundary-guard.sh ; echo "退出码=$?"

# 5. boundary-guard —— 界内应静默 exit 0
echo '{"tool_name":"Write","tool_input":{"file_path":"README.md"}}' \
  | CLAUDE_PROJECT_DIR="$(pwd)" bash .claude/hooks/boundary-guard.sh ; echo "退出码=$?"

# 6. harness-check —— 名字对得上时应零输出
echo '{}' | CLAUDE_PROJECT_DIR="$(pwd)" bash .claude/hooks/harness-check.sh

# 7. harness-check —— 复制到别的名字下应打印仪式指令
cp -R . /tmp/renamed-project-test
echo '{}' | CLAUDE_PROJECT_DIR=/tmp/renamed-project-test bash .claude/hooks/harness-check.sh
rm -rf /tmp/renamed-project-test
```

## 10. 脚本：只有一个，其余仍暂缓

**已有的唯一一个**：

| 项 | 状态 | 说明 |
|---|---|---|
| `scripts/init-repos.sh` | ✅ 已有 | 把**公开分发的压平快照**还原成一个可用的 git 仓库：给仓库根 `git init -b main`（已是仓库则跳过）+ 启用 `core.hooksPath`（**回读验证**）+ 首次提交。幂等，重复跑无副作用；若在树里发现嵌套 `.git` 会打印警告（那是旧形态残留）。🔴 **它只还原根仓库一个**——本模板仓库自己是单一仓库，而不是本规范 §4 教的独立嵌套形态，两套口径的分界见 [`02-设计决策.md`](02-设计决策.md) **D11**。脚本本身的立项理由见 **D10** |

**仍然暂缓（一个都没写）**：

| 项 | 状态 | 说明 |
|---|---|---|
| `scripts/new-project.sh` | **暂缓，已拍板** | 复制 + 改名 + `git init` + 启用 hooksPath + 清示例内容，一条命令完成 |
| `scripts/check-all.sh` | 计划中 | 遍历 `projects/`，检查每个子项目的 hooksPath / HARNESS-STATUS / README 索引是否健全 |
| `scripts/sync-index.sh` | 计划中 | 扫 `projects/` 自动更新父项目 README 的索引表 |

🔴 **暂缓的理由**见 [`02-设计决策.md`](02-设计决策.md) D7：现阶段项目数量少，手工做一遍能让人真正记住机制；
脚本写早了会变成「不知道它替我做了什么」的黑盒。

**不要自作主张先把脚本写了。** `init-repos.sh` 之所以是例外，是因为它做的事**不需要任何判断**
（每个单元四条一模一样的命令，判据是机械的），而且不做的话公开分发根本不可用——
它跟那三个的逐项对照见 [`02-设计决策.md`](02-设计决策.md) D10。
