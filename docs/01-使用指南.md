## 0. 从 GitHub 获取（如果你是从公开仓库来的，先做这一步）

```bash
git clone https://github.com/dusword/agent-project-scaffold.git
cd agent-project-scaffold
bash scripts/init-repos.sh          # 🔴 必做，见下面「为什么必须跑」
```

跑完你只会看到**一个**仓库被处理（就是你 clone / 解压出来的这个根目录）——
本模板仓库自己是**单一仓库**，模具与四类 demo 都装在它里面（见
[`02-设计决策.md`](02-设计决策.md) D11）。
之后就跟本地复制流程**完全汇合**：直接往下看 §1「复制什么，得到什么」，
§2 选型、§3 确立仪式、§4 手工步骤清单一条都不用改。

### 🔴 为什么必须跑这一步（不是可选的便利）

公开仓库是一份**压平的快照**：文件全在，**源头那份 git 历史不随分发**
（这条是死规矩，理由见 [`03-发布与同步.md`](03-发布与同步.md) §1）。

| 随分发过来了 | 没有随分发过来 |
|---|---|
| 全部文件（含 `.claude/` `.githooks/` 这些点目录） | 源头仓库的 git 历史 |
| 三份说明书 + 一份维护者手册 + 出厂纯净的成品 + 四类 demo | 「一条日志 = 一次提交」的历史示范 |

而你手上这份**具体缺什么，取决于你怎么拿的**：

| 你怎么拿的 | 有没有 `.git` | 有没有 `core.hooksPath` |
|---|---|---|
| GitHub **zip 下载** | ❌ 没有 | ❌ 没有 |
| `git clone` | ✅ 有 | ❌ **没有**——它是仓库的**本地配置**，从来不随 clone 过来 |

🔴 **两种情况都得跑脚本**，因为**提交硬闸靠的是 `core.hooksPath`，而它两种情况下都不在**。
不跑的后果**不是报错，是静默失效**：整套「改动必留日志」的纪律一声不吭地不存在。
这正是 §6 坑 1 那件事，只是发生在整棵树上。

脚本做的四件事：`git init -b main`（已经是仓库就跳过，不碰历史）→
`git config core.hooksPath .githooks`（并**回读验证**）→ `git add` → 首次提交。
**只做根仓库一个。幂等**，重复跑没有副作用。
设计理由见 [`02-设计决策.md`](02-设计决策.md) D10（脚本为什么存在）与 D11（为什么只做一个）。

### ⚠️ 两件如实说明

1. **「一条日志 = 一次提交」在分发的这一份里对不上号。** 跑完脚本整棵树只有 1 次提交
   （`chore: 从模板初始化仓库`），而 7 个项目单元的 `CHANGE-LOG.md` 里各躺着一整串历史记录
   （少的 9 条，多的二十几条）。
   这不是坏了——那些记录属于源头的历史，随文件过来了，随历史没过来。
   🔴 **这个不变量在你自己新建的项目里从第一天起就成立**：按 §4 建项目时你会清空示例记录、
   写下第一条真实记录、做第一次提交，从那以后 `git log --oneline | wc -l` 与
   `grep -cE '^\| [0-9]{4}-' CHANGE-LOG.md` 就该永远相等（自测命令见
   [`00-架构规范.md`](00-架构规范.md) §9 第 3b 条）。
2. 🔴 **往模具的 `projects/` 下新增文件时，git 会把它挡在暂存区外。** 因为模具与 `demo-parent-project`
   自己的 `.gitignore` 里写着 `projects/`——那是它们的**出厂形态**（它们要教给真实项目的正是
   「父仓库排除 `projects/`」），刻意保留，不该改。
   要在这份分发副本里往那些子树加文件，得显式强制：`git add -f <路径>`。

   🔴 **它喊不喊，取决于你怎么写 `git add`**（实测三种表现，别只记住一种）：

   | 情形 | 输出 | 退出码 | 进暂存区了吗 |
   |---|---|---|---|
   | 用**显式文件路径** add 被忽略的**新**文件 | 打印 `The following paths are ignored by ...` | 1 | ❌ 没有 |
   | 用**宽泛 pathspec**（`git add projects/`）扫到它们 | 🔴 **零输出** | 0 | ❌ 没有 |
   | add 一个 `projects/` 下**已被跟踪**的文件 | 照样打印那段忽略警告 | 1 | ✅ **加进去了** |

   所以真正会咬人的是**宽泛 pathspec** 那一种——只写显式路径就一定会喊。
   ⚠️ 另外第三种有个摩擦：`git add <已跟踪文件> && git commit -m "..."` 里的 `&&`
   会被那个退出码 1 短路，**`commit` 根本不执行**。**`add` 与 `commit` 分两行写**，
   暂存成没成看 `git diff --cached --name-only`，不看 `add` 的退出码。

   漏网检查（正常应输出 `CLEAN`）：

   ```bash
   out=$(git ls-files --others --ignored --exclude-standard -- projects/ \
         | grep -vE '__pycache__|\.pytest_cache/')
   [ -z "$out" ] && echo "CLEAN: 没有漏网文件" || printf '%s\n' "$out"
   ```

   **这只影响你手上这份分发副本**——照 §4 复制模具建出来的项目，`projects/` 被自己的父仓库
   排除是**正确行为**，子项目本来就该各自 `git init`（[`00-架构规范.md`](00-架构规范.md) §4）。

## 1. 复制什么，得到什么

**只有两种动作**，记住这张表就够了：

| 你复制的东西 | 你得到的东西 | 放到哪 |
|---|---|---|
| 整个 `main-sub-architecture-project-demo/` | 一个新的**总项目**（下面能挂子项目） | 任意位置，通常与别的项目并列 |
| 成品 `projects/` 下的某一个 demo | 一个新的**子项目**（对应那一类范式） | 某个已有项目的 `projects/` 下 |

🔴 **「子项目」不限层级。** 父项目和子项目是同一套骨架，区别只是「有没有 `projects/` 目录」。
所以你可以把一个 demo 复制到孙项目的 `projects/` 下，再往下嵌——**层数没有上限**。
成品里 `demo-parent-project/projects/mini-child-code-project` 就是现成的三层例子。

### 成品的四个 demo 在哪

| demo | 类型 | 复制它得到 |
|---|---|---|
| `projects/demo-code-project` | 代码项目 | 一个带 `src/` `tests/` `docs/` 的代码项目骨架 |
| `projects/demo-experiment-project` | 实验项目 | 一个带 `EXPERIMENTS.md` `experiments/` 的实验项目骨架 |
| `projects/demo-docs-project` | 文档仓库 | 一个带 `inbox/` `archive/` 的知识仓库骨架 |
| `projects/demo-parent-project` | 父项目 | 一个只管秩序、下面能再挂子项目的父项目骨架 |

## 2. 选型：该建哪一类

**一句话判据：你最终要交付的那个东西，长什么样？**

| 如果你会这么说…… | 那就是 | 复制 |
|---|---|---|
| 「做完之后**有个东西能运行**」 | 代码项目 | `demo-code-project` |
| 「做完之后**知道该选哪条路**」 | 实验项目 | `demo-experiment-project` |
| 「做完之后**有份东西以后要一直翻**」 | 文档仓库 | `demo-docs-project` |
| 「它自己不产出内容，**它管着一堆产出内容的**」 | 父项目 | `demo-parent-project` |

### 判不准的三种常见情形

| 情形 | 怎么判 |
|---|---|
| 又要写代码又要做实验 | 看**代码是不是交付物**。代码只是为了得出结论 → **实验项目** |
| 又要写文档又要写代码 | 看**文档是不是给别人反复查的**。只是自己项目的说明 → **代码项目**，文档放它的 `docs/` |
| 一个主题下有好几件性质不同的事 | 别硬塞进一个项目。**建父项目**，把不同性质的事拆成不同类型的子项目 |

最后一条尤其重要：**类型不同则纪律不同**，硬塞在一起的结果是两套纪律互相打架，最后哪套都不执行。
成品的 `demo-parent-project` 就是照着这个理由拆的，它的 `docs/00-统筹说明.md` §1 有完整论证。

🔴 **判错不致命。** 四类的骨架是同一套，改的只是 `CLAUDE.md` 里的范式段落。
发现判错了，改宪法 + 在 CHANGE-LOG 记一条，就完事了，不用重建项目。

## 3. 🔴 复制改名后会发生什么（先看懂这个，再动手）

**复制 + 改名之后，下次在新目录里开 Claude 会话，会自动弹出「确立仪式」的提示。**
这是刻意设计的机关，不是 bug，也不需要你做任何重置动作。

原理：`.claude/hooks/harness-check.sh` 挂在 `SessionStart` 上，每次开会话读
`.claude/HARNESS-STATUS.md`，比较里面记的项目名和当前目录名：

```
demo-code-project/       状态文件记「demo-code-project」= 目录名 → 安静，零输出
       ↓ 复制 + 改名
my-new-tool/             状态文件仍记「demo-code-project」≠ 目录名 → 触发仪式
```

**复制改名这个动作本身就把状态弄「脏」了，而脏状态正是我们要的信号。**
所以：

| 常见疑问 | 答案 |
|---|---|
| 要不要手工清空 `HARNESS-STATUS.md`？ | 🔴 **不要。** 留着让它对不上名字，仪式会自己来。手工清反而多一步会忘 |
| 要不要写个重置脚本？ | 不需要。这就是不用脚本的原因——机制自带触发，忘不掉 |
| 仪式会做什么？ | agent 读背景 → 一次问你 3~5 个问题 → 按需改宪法 → 把结果写回状态文件。四步细则见 `.claude/rules/harness-setup.md` |
| 允许一字不改宪法吗？ | 🔴 **允许**，那也是有效的确立结果，如实写「沿用默认，未作改动」即可 |
| 我赶时间想跳过？ | 直说「跳过」。agent 会照办，但下次开会话还会再提示一次 |
| 只是给目录改个名也会触发？ | 会。这是可接受的副作用——目录改名通常意味着定位变了，重新对一次规矩本来就该做 |

⚠️ **仪式的「确认人」必须是真人。** agent 不许自己填一个名字把状态文件改了——
那等于伪造了一次没发生过的确认。

## 4. 手工步骤清单

> 🔴 **目前没有脚本，也不要自己造一个**（理由见 [`02-设计决策.md`](02-设计决策.md) D7）。
> 手工做一遍能让你真正记住机制，而这套机制的每一步都有理由。

### 4.1 新建一个总项目

```bash
# 1. 复制整个成品，改成新名字
cp -R <成品路径> <目标位置>/my-new-project
cd <目标位置>/my-new-project

# 2. 删掉复制来的 .git（复制来的历史属于成品，不属于你）
#    ⚠️ 现在这一步通常是**空操作**：模具自己不带 .git（见下面的说明）。
#       保留它是为了兼容「从别处、或从旧形态复制过来」的目录，跑一下不会有坏处。
rm -rf .git

# 3. 重新 git init
git init -b main

# 4. 🔴 启用提交硬闸（每个仓库一次，clone 下来也要重做）
git config core.hooksPath .githooks
git config --get core.hooksPath        # 应输出 .githooks
```

⚠️ **`cp -R` 不会给你带来任何嵌套 `.git`。** 模板仓库自己是单一仓库（`02` D11），
模具与它下面的四个 demo **都没有自己的 `.git`**——它们的历史全在模板仓库那一份里，
复制目录带不走。所以复制完你的新项目里一个 `.git` 都没有，第 3 步的 `git init` 是从零开始。

🔴 **由此来的一件必须做的事**：你**留下**的每一个 demo，都还**不是 git 仓库**。
而你的新项目根 `.gitignore` 排除整个 `projects/`（这是
[`00-架构规范.md`](00-架构规范.md) §4「独立嵌套仓库」的核心约定），
于是那个 demo 目录**谁都不跟踪**——根仓库不管它，它自己也没有仓库。
**这个状态不报错**，正是本体系最怕的那类故障。所以留下来的 demo 要各自补齐两步：

```bash
cd projects/<你留下的那个 demo>
git init -b main
git config core.hooksPath .githooks
git config --get core.hooksPath        # 应输出 .githooks
```

（打算删掉的 demo 就不用管了，第 5 步删掉即可。）

⚠️ §5 自检清单第 3 条（`git log` 没有成品历史）**只查根仓库**，查不出上面这一层。

然后手工做这几件事：

| # | 做什么 | 注意 |
|---|---|---|
| 5 | 🔴 **先决定复制源，再删 `projects/` 下的 demo** | 见下面「复制源从哪来」。**不要无脑全删**——删光之后建第一个子项目就没样板可复制了 |
| 6 | 改写 `README.md`：自我介绍改成你的项目，子项目索引表按实际保留情况改 | 开头两三段说清「我是谁 / 交付什么 / 怎么维护」 |
| 7 | 清空 `CHANGE-LOG.md` 的示例记录，写第一条真实记录 | 第一条通常是「立项：宪法 + 钩子 + 骨架」。🔴 **在这条记录里写明本项目是从哪份模具复制来的（模具的路径）**——将来找复制源就靠它 |
| 8 | 改写 `CLAUDE.md`——**或者先别改** | 宪法会在确立仪式里对着你的回答改，先留着也行 |
| 9 | 🔴 **改写 `docs/` 里带过来的示范文档** | 模具的 `docs/00-项目说明.md` 写的是**模具自己**的实况（在描述那四个 demo）。复制过来后它立刻失真，而宪法把它列为「新会话第一件事」的第 3 项——**改写成你自己项目的统筹说明，或者删掉并同步 README 索引** |
| 10 | 🔴 **不要碰 `.claude/HARNESS-STATUS.md`** | 留着让它对不上名字，仪式自己会来（见 §3） |
| 11 | 首次提交：`git add <显式路径> && git commit` | 不用 `-A`；`CHANGE-LOG.md` 必须在暂存区里，否则被硬闸拒绝 |

#### 🔴 复制源从哪来（第 5 步的判据，别跳过）

宪法「新建子项目七步」的第 2 步是**复制一个同类型的现有子项目**。
所以 `projects/` 一旦删空，**你的第一个子项目就没有源可复制**——
这个洞在实测里真的绊住过：会话只能停下来问人要模具路径。

两条路，选一条，**在建项目的时候就选**：

| 选项 | 怎么做 | 适合 |
|---|---|---|
| **A. 留一份样板**（省事，推荐） | 保留你最常用的那一类 demo（比如代码项目留 `demo-code-project`），把它清成空壳骨架、改写它的 README/CHANGE-LOG，当本项目的复制源 | 你会反复建同一类子项目 |
| **B. 全删，记住模具在哪** | 四个全删，但**把模具的路径写进第 7 步那条立项记录里**（例：「本项目复制自 `<模具路径>`」） | 你想要一个完全干净的 `projects/` |

选 B 时，将来建第一个子项目就是这么找源的：**读本项目 `CHANGE-LOG.md` 最早那条立项记录，
里面写着模具在哪，去那儿取对应类型的样板。** 记录里没写就去问项目主人——
🔴 **不要凭猜去找，更不要从零手搓一套骨架**（手搓的骨架一定漏钩子，而漏了钩子不会报错）。

### 4.2 新建一个子项目

```bash
# 1. 判断类型（§2），复制一份同类型的样板到目标父项目的 projects/ 下
#    复制源按这个顺序找：① 该父项目 projects/ 下已有的同类型子项目
#                        ② 没有 → 该父项目 CHANGE-LOG 最早那条立项记录里写的模具
cp -R <同类型样板路径> <父项目>/projects/my-new-tool
cd <父项目>/projects/my-new-tool

# 2~4. 同上：删 .git、重新 init、启用 hooksPath
rm -rf .git
git init -b main
git config core.hooksPath .githooks
```

然后：

| # | 做什么 | 注意 |
|---|---|---|
| 5 | 清掉 demo 的示例内容 | `src/` 的示例代码、`EXPERIMENTS.md` 的示例轮次、`archive/` 的示例文档等。**保留骨架与格式示范** |
| 6 | 改写 `README.md` / `CHANGE-LOG.md` | 同上 |
| 7 | 🔴 **不改 `HARNESS-STATUS.md`** | 留给确立仪式 |
| 8 | 首次提交 | 同上 |
| 9 | 🔴 **回到父项目**：README 索引表加一行（含**状态**列，新建时填 🚧 进行中）+ CHANGE-LOG 记「新增子项目 X」，然后在**父项目**提交 | 🔴 那条记录必须写明**来由**：因哪个需求 / 哪份调研 / 哪条实验结论而建（一句话就够）。见下面的警告 |

⚠️ **第 9 步没有钩子兜底，纯靠纪律。**
`pre-commit` 规则二本来管「`projects/` 下有新增就要求同步 README」，
但 `projects/` 被父仓库 `.gitignore` 排除了，**git 根本看不到那次新增，规则二不会触发**。
这是已知局限，详见 [`02-设计决策.md`](02-设计决策.md) L3。**加了子项目就手动去更新父项目的索引表。**

## 5. 建完的自检清单

新项目建完，逐条核对（在新项目根目录下）：

- [ ] `git config --get core.hooksPath` 输出 `.githooks`
- [ ] `CLAUDE.md` 在**项目根**，且 `.claude/CLAUDE.md` **不存在**（两处并存会被重复加载）
- [ ] `git log --oneline` 只有你自己的记录，**没有成品的历史**（`.git` 删干净了）
      ⚠️ 这条**只查根仓库**。你留下来的每个 demo 都得自己 `git init` + 设 `core.hooksPath`，
      这条查不出它们漏没漏，见 §4.1 的说明
- [ ] 随便改一个文件试提交，被 `pre-commit` 拒绝并提示补 CHANGE-LOG ✅
- [ ] 再试一次：只把上一条 CHANGE-LOG 记录**改几个字**（不新起一行）提交，
      仍被拒绝并提示「要另起一行」✅（这是规则一之二，见 [`00-架构规范.md`](00-架构规范.md) §6.1）
- [ ] `.claude/HARNESS-STATUS.md` 里的项目名**故意**对不上目录名（等仪式来改）
- [ ] `/usr/bin/grep -rn "/Users/" . --exclude-dir=.git` 无结果（没有绝对路径泄漏）
      🔴 **必须写死 `/usr/bin/grep`，不能裸写 `grep`**：PATH 上的 `grep` 可能是 ugrep 一类的替代品，
      它们**默认遵守 `.gitignore`**——而父项目的 `.gitignore` 正好排除整个 `projects/`，
      于是所有子项目被静默跳过，**「无结果」就成了假信号**（教训见
      [`02-设计决策.md`](02-设计决策.md) **L12**）。用前一秒钟自校准：让它去找一个**确定存在**的字符串，
      比如 `/usr/bin/grep -rl '项目' --include=CLAUDE.md . --exclude-dir=.git | wc -l`
      要等于 `find . -name CLAUDE.md | wc -l`；两个数对不上，这个扫描器说的话一句都不能信。
      另外排掉编译产物目录（`--exclude-dir=__pycache__ --exclude-dir=.pytest_cache`），
      `.pyc` 里嵌着本机绝对路径，会一直误报
- [ ] README 开头两三段说清了「我是谁 / 交付什么 / 怎么维护」，主体是索引表
- [ ] README 的自我介绍里有一句**来由**（为什么存在 / 源自哪里），见 [`00-架构规范.md`](00-架构规范.md) §5 第 5 条
- [ ] （父项目）子项目索引表有「**状态**」列，取值是生命周期四态
      （🚧 进行中 · ⏸ 暂停 · ✅ 已完成 · 🗄 已放弃（留档）），不是「能不能跑」
- [ ] `docs/` 里没有还在描述模具自己内容的文档（`00-项目说明.md` 已改写或已删并同步 README）
- [ ] 🔴 **第一个子项目的复制源已经有着落**：`projects/` 下留了同类型样板，
      **或者** `CHANGE-LOG.md` 的立项记录里写了模具路径（见 §4.1「复制源从哪来」）
- [ ] （子项目）父项目 `README.md` 的索引表里有这个新项目

钩子的机械自测命令见 [`00-架构规范.md`](00-架构规范.md) §9。

## 6. 日常使用中最容易踩的四件事

| # | 坑 | 后果 | 怎么避免 |
|---|---|---|---|
| 1 | 忘了 `git config core.hooksPath .githooks` | **提交硬闸静默失效**，一声不吭 | 建完就跑一次 `git config --get core.hooksPath` |
| 2 | 用 `git add -A` 提交 | 卷进没打算提交的东西，而 CHANGE-LOG 那一条记录写不全 | 一律 `git add <显式路径>` |
| 3 | 把子项目的变化记进父项目 CHANGE-LOG | 写了一份**没有对应提交的假历史**（`projects/` 被 ignore，父仓库压根没那次改动） | 父级日志只记父级：新增/归档子项目、改统筹文档、改自己的规矩 |
| 4 | 在父项目的会话里顺手改子项目的文件 | 改动无日志、无审阅、上下文错位 | 🔴 **`boundary-guard.sh` 拦不住这个**（子项目就在父项目树里，见 §7）。纯靠纪律：去子项目目录开会话改。**已经在父会话里改了 → 按 §8 把提交做对** |

## 7. 我该在哪个目录开会话

**在哪个项目干活，就在哪个项目的根目录开会话。** 理由有三个，条条是硬的：

| 理由 | 说明 |
|---|---|
| 钩子按项目根加载 | `$CLAUDE_PROJECT_DIR` 决定 `boundary-guard.sh` 拿哪个目录当边界。⚠️ 子项目在父项目树**内**，所以这个方向**钩子拦不住**，纪律得自己守 |
| 宪法按项目根加载 | 你读的是这个项目的 `CLAUDE.md`。跑到别的树里改东西 = 拿 A 的规矩改 B 的代码 |
| 提交要在那个仓库里做 | 每个项目是独立仓库，有自己的 CHANGE-LOG 和硬闸 |

⚠️ **模板仓库自己是个例外**：它是单一仓库（`02` D11），模具与 demo 与它同仓，
所以在模具厂的会话里直接改模具是正常的同仓改动，不再需要换目录——
但提交硬闸会按**项目单元**要求「动了哪个单元就补哪个单元自己的那行日志」。
**这条只对模板仓库成立**；你按本指南建出来的项目是独立嵌套形态，上面三条理由条条照旧。

## 8. 在父项目会话里跨子项目干活：能做，但提交要这么做

项目主人 2026-08-19 提的真实疑问：

> 「假如我在父项目起了 claude 会话，要求父项目处理两个子项目的开发工作，
> 然后当我要进行 git 提交的时候，我是否能正常操作？因为对父项目来说，子项目被 git 排除了。」

**答案：能正常操作。** 但要先把它理解成正确的形状——**这不是一次提交，是几个仓库、几次提交。**

### 8.1 几个仓库，几次提交

| 改动落在哪 | 在哪提交 | 谁把关 |
|---|---|---|
| 子项目 A 的文件 | A 自己的目录（`git -C projects/A ...` 或 `cd` 过去，都行） | A 的 `pre-commit`：要 **A 自己的** `CHANGE-LOG.md` 净增一条记录 |
| 子项目 B 的文件 | B 自己的目录 | B 的 `pre-commit`：要 **B 自己的** `CHANGE-LOG.md` 净增一条记录 |
| 父项目自己的文件（索引表 / 统筹文档 / 父日志） | 父项目根 | 父项目的 `pre-commit` |

动了三个仓库就是三次提交，每次各带各自那一条日志记录。
**agent 在父项目会话里可以把这几次提交全代办掉**——钩子按仓库各自加载、各自生效，互不干扰。

🔴 **不要试图把子项目的改动提进父仓库。** `projects/` 被父 `.gitignore` 排除是**故意的**
（见 [`02-设计决策.md`](02-设计决策.md) D1）：不排除的话，内嵌仓库会被父仓库记成一个
**commit 指针**（gitlink），父仓库存的只是「这个子仓库当前停在哪个 commit」，
子项目每提交一次、父仓库就得跟着更新一次指针——与「父级日志只记父级」直接打架。

### 8.2 🔴 真正的坑：父根 `git status` 永远是干净的

本节最要紧的一句：**父仓库的 `git status` 看不见任何子项目的脏改动。**
跨子项目干完活，在父根跑 `git status` 显示一片干净——而某个子项目里可能还躺着一堆没提交的改动。

所以**不许拿父根的 `git status` 当「全都提交完了」的凭据**，它答的只是父仓库自己。两条办法：

1. **逐个仓库查**：这次动过的每一个子项目都跑一遍 `git -C projects/<名> status --short`。
2. **全树扫描**（推荐，一条命令扫完整棵树，在树根跑）：

```bash
find . -type d -name .git -not -path "*/.git/*" | while read g; do d=$(dirname "$g"); [ -n "$(git -C "$d" status --porcelain)" ] && echo "🔴 $d 有未提交改动"; done
```

**没有任何输出 = 这棵树上所有仓库都干净。** 有输出就按 §8.1 去那个目录补提交。

### 8.3 能做 ≠ 推荐：这么干你放弃了什么

在父会话里跨子项目干活，有两件事**没有发生**：

| 少了什么 | 后果 |
|---|---|
| 子项目的**确立仪式检查**没跑过 | `harness-check.sh` 挂在会话启动上，按**开会话的那个目录**判定。父会话只检查父项目 |
| 子项目的**宪法**没被完整加载 | 你读的是父项目的 `CLAUDE.md`；子项目的宪法只在 agent 真的碰到它目录里的文件时才被带进上下文——**等于拿 A 的规矩改 B 的东西** |

而且这个方向 `boundary-guard.sh` **拦不住**（子项目物理上就在父项目树内，见 [`02-设计决策.md`](02-设计决策.md) L6）。
所以口径不变：**正式开发去子项目目录单开会话**（§7）。本节答的是另一个问题——**已经在父会话里改了，怎么把提交做对。**

🔴 **但你明确要求 agent 在父会话里跨子项目干活时，它该照办**，按 §8.1 把每个仓库各提交一次，
而不是拿「边界」那条一口回绝。实测确认过这个失败形状：一个无头会话被要求「改子项目 README + 改父项目文档 + 都提交好」，
它**只做了父项目那半**就停了，理由是「改子项目算越界，去子项目目录开会话」——活只干了一半。
两份宪法（成品根 / `demo-parent-project`）里那段精炼版已把这条写进去。
