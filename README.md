# agent-project-scaffold

**给人和 AI agent 共用的多项目治理模板**——一套「总项目 - 多子项目」的目录约定，
配三个真的会拦住你的钩子，以及一份可以直接复制走开新项目的模具。

## 解决什么问题

一个大目标不可能一口吃下，它必然被拆成很多小任务；而调研和实验做着做着，
又会不断催生「这条路值得单独试一下」的新方向——有的成，有的死。
于是桌面上慢慢堆出一堆互不相干、来由不明的文件夹：**哪个还活着？这个当初为什么建的？**
半年后没人答得上来，而放弃过的方向连「这条路不通」这点知识都没留下。

这套模板让所有尝试**长在同一棵树上**：目录树就是任务拆解树，每个节点写明自己因什么而生，
做完了标已完成，做不下去了标**已放弃并留档**（放弃的方向是资产不是垃圾），
而且规矩不靠自觉——**提交没写日志会被直接拒绝**。
人和 AI agent 守的是同一套规矩，读的是同一批文件。

> 完整的立法意图（四条意图 + 一条真实的拆解链）见 [`docs/00-架构规范.md`](docs/00-架构规范.md) §0。

## 快速开始

```bash
# 1. 拿到模板
git clone https://github.com/dusword/agent-project-scaffold.git
cd agent-project-scaffold

# 2. 🔴 必做：把根仓库还原出来（GitHub 分发是压平快照，不带 .git）
#    幂等，重复跑没有副作用；用 git clone 拿到的已经有 .git，脚本只补验一次 hooksPath
bash scripts/init-repos.sh

# 3. 复制模具，改成你自己的项目名
cp -R projects/main-sub-architecture-project-demo ../my-new-project
cd ../my-new-project
rm -rf .git && git init -b main         # 模具不带自己的 .git，rm 这一步通常是空操作
git config core.hooksPath .githooks     # 🔴 启用提交硬闸，每个仓库各做一次
git config --get core.hooksPath         # 应输出 .githooks

# 4. 在新项目目录里开一个 Claude Code 会话
#    → 「确立仪式」会自动触发，引导你把通用规矩贴合到这个项目
claude
```

第 4 步不需要你记得做任何事：模具里记的项目名和新目录名对不上，
会话启动时钩子自己就发现了（原理见下面「核心特性」第 1 条）。

**完整步骤清单**（改哪几个文件、留不留 demo、建完怎么自检）见
[`docs/01-使用指南.md`](docs/01-使用指南.md)——从 GitHub 来的先看它的 §0。

## 核心特性

| 特性 | 一句话 |
|---|---|
| **确立仪式自动触发** | 模具被复制改名后，记录的项目名和目录名对不上，下次开 AI 会话自动要求先把规矩对齐一遍。**不需要跑任何重置脚本，所以不可能忘** |
| **提交硬闸** | 改了东西却没在 `CHANGE-LOG.md` 里新增一行记录，`git commit` 直接被拒——而且**改写上一条旧记录不算新增**。没有跳过开关。🔴 判定**按「项目单元」**（= 向上找到的最近一个含 `CLAUDE.md` 的目录）：一个仓库里并排装几个项目时，动哪个单元就要求**那个单元自己的**日志净增一行；单项目仓库里只有根一个单元，行为与旧版逐条等价 |
| **结构变化必更索引** | 某个单元的 `docs/` 或 `projects/` 下有文件新增 / 删除 / 改名，**那个单元的** `README.md` 必须一起提交，否则拒绝。索引失真是 agent 最容易被误导的地方 |
| **越界护栏** | AI 会话想写本项目树以外的文件，工具调用被拦下。真要跨项目改，走一个写放行条的授权流程（30 分钟自动过期） |
| **生命周期四态 + 放弃留档** | 每个子项目在父项目索引表里必须标状态：🚧 进行中 · ⏸ 暂停 · ✅ 已完成 · 🗄 已放弃（留档）。**放弃的不许删目录**，只改状态 + 写清「为什么停 / 验证到哪 / 若重启从哪接」 |
| **来由可追溯** | 每个项目的自我介绍必须答「我因什么而生」，父项目索引表里也要带上。半年后你还能查到这个目录为什么存在 |
| **四类项目范式** | 代码 / 实验 / 文档 / 父项目，骨架完全相同、纪律各不相同。判据一句话：**你最终要交付的那个东西长什么样** |
| **无限递归** | 父项目和子项目是同一套骨架，区别只是有没有 `projects/` 目录。子项目自己可以当父项目，层数没有上限 |
| **局限如实写出来** | 每个钩子都在自己的注释和文档里写明**它拦不住什么**（`--no-verify` 绕得过去、父项目改子项目拦不住……）。**假的安全感比没有安全感更危险** |

```
├── README.md                            本文。人的落地页 + agent 的目录索引
├── CHANGE-LOG.md                        本项目的历史，一条记录 = 一次提交

├── .claude/                             AI 会话侧的装置：宪法细则 / 钩子 / 确立状态
│   ├── rules/                           三条规矩：项目边界 / 文档纪律 / 确立仪式手册
│   ├── hooks/                           越界拦截（PreToolUse）+ 确立仪式触发器（SessionStart）
│   ├── settings.json                    把上面两个钩子挂到 Claude Code 上
│   └── HARNESS-STATUS.md                确立状态。🔴 记的项目名 ≠ 目录名就会触发仪式
├── .githooks/pre-commit                 提交硬闸：改动必留日志、结构变化必更 README
└── projects/                            子项目目录。🔴 本仓是单一仓库，这里**全部纳入 git 跟踪**
    │                                    （demo 是本仓的展品，不再各自 init；但它们仍是独立「项目单元」）
    └── main-sub-architecture-project-demo/   ← 🔴 模具本体，复制它开新项目
        ├── CLAUDE.md / README.md / CHANGE-LOG.md / docs/    一个正常总项目该有的样子
        ├── .claude/ / .githooks/                            同一套 harness
        └── projects/                                        四类样板 + 一个孙项目
            ├── demo-code-project/          代码项目样板：单位换算器，39 个测试
            ├── demo-experiment-project/    实验项目样板：EXPERIMENTS.md 只增不改，含一条负面结论
            ├── demo-docs-project/          文档仓库样板：inbox/ 收材料、archive/ 放归档
            └── demo-parent-project/        父项目样板，它下面还挂着一个孙项目（三层例子）
```

**模具为什么不在本仓库根目录**：说明书和成品必须分家。
模具会被复制几十次，如果「模板怎么用」写在模具里面，每个新项目一出生就背着一份不属于它的说明书。
所以说明书全留在这里的 `docs/`，出厂的只有干净的模具（取舍见 [`docs/02-设计决策.md`](docs/02-设计决策.md) D8）。

## 🤖 如果你是 AI agent

**人类读 README，agent 读 `CLAUDE.md`。两个入口都在，别只读一个。**

进入**任何**一个按本体系搭起来的项目时，按这个顺序做：

| # | 做什么 | 为什么 |
|---|---|---|
| 1 | **先看会话启动时注入的内容** | 若 harness 未确立，`SessionStart` 钩子会往你的上下文注入一段「先做确立仪式」的指令，**那是本次会话的第一要务**，先做完再做别的事 |
| 2 | 读**当前项目根**的 `CLAUDE.md` | 那是这个项目的宪法：它属于四类中的哪一类、纪律是什么、边界在哪 |
| 3 | 读 `README.md` 的索引表 | 靠它**决定读哪个文件**，不要把整棵树读一遍 |
| 4 | 读 `.claude/rules/*.md` | 逐条可执行的细则（边界 / 文档纪律 / 确立仪式操作手册） |
| 5 | `git status --short` + `git log --oneline -5` | 看清现状，别假设 |

🔴 **每个项目有自己的宪法和自己的确立状态。** 父项目的 `CLAUDE.md` 不管子项目的事——
子项目有独立宪法、独立 `CHANGE-LOG.md`，在独立嵌套形态下还是独立 git 仓库。
**在哪个项目干活，就在哪个项目的根目录开会话**（理由见 [`docs/01-使用指南.md`](docs/01-使用指南.md) §7）。
（⚠️ 本仓库自己是个例外：它是单一仓库，`projects/` 下的模具与 demo 与它同仓，
但**各自仍是独立的「项目单元」，日志各记各的**。见 [`docs/02-设计决策.md`](docs/02-设计决策.md) D11。）

几条你一定会撞上的硬规矩：

- **提交必须带日志**：改了任何文件，`CHANGE-LOG.md` 要**新增一行**记录再一起提交。改旧行不算。
- **不用 `git add -A`**，用显式路径。理由是每次提交都要对应日志里那一条记录。
- **一次会话动了几个单元，就要有几条日志记录**，各记各的。
  🔴 **两种形态，看清你在哪一种**：
  - **独立嵌套形态的真实项目**（体系教的那套）：几个仓库就几次提交；父仓库的 `git status`
    **看不见子项目的脏改动**，别拿它当「全都提交完了」的凭据（全树扫描命令见指南 §8.2）。
  - **本仓库**（单一仓库）：`git status` **看得见全树**，一次提交可以同时动多个单元，
    但提交硬闸 v2 会要求**每个被动到的单元各补自己的那行日志**——只记根日志会被拒。
- **不许写本项目树以外的文件**，要跨界走 [`.claude/rules/boundary.md`](.claude/rules/boundary.md) §3 的授权流程。
- **不许伪造确立仪式**：状态文件里的「确认人」必须是真人，不能是你自己。

### 🔴 关于 `projects/` 的两件事

1. **它已经纳入本仓库的 git 跟踪**（2026-08-25 起，本仓是单一仓库，见
   [`docs/02-设计决策.md`](docs/02-设计决策.md) D11）。所以在这里 `git status` **看得见全树**，
   模具与 demo 的脏改动都在里面。

   ⚠️ **但模具与 `demo-parent-project` 自己的 `.gitignore` 里仍然写着 `projects/`**——
   那是它们的**出厂形态**（它们要教给真实项目的就是「独立嵌套、父仓库排除 projects/」），
   **一个字都不该改**。代价是：往这两棵子树的 `projects/` 里**新增文件时，git 会静默忽略它**，
   必须显式强制加：

   ```bash
   git add -f <路径>
   ```

   🔴 **漏网检查**（改完提交前跑一次，正常应当输出 `CLEAN`）：

   ```bash
   out=$(git ls-files --others --ignored --exclude-standard -- projects/ \
         | grep -vE '__pycache__|\.pytest_cache/')
   [ -z "$out" ] && echo "CLEAN: 没有漏网文件" || printf '%s\n' "$out"
   ```

   （过滤掉的两类是 demo 代码项目跑测试留下的运行时垃圾，本来就该被忽略。）

2. **新建子单元后要手工回来更新上面的索引表**（+ 记一条 CHANGE-LOG）。
   `pre-commit` 规则二**在这个方向上仍然不会替你兜底**：新单元自己的 `CLAUDE.md` 跟着同一次提交
   进索引，于是那批文件全部归**新单元**，不触发父单元的规则二。
   **这一步靠纪律**（局限说明见 [`docs/02-设计决策.md`](docs/02-设计决策.md) L3）。

## ⚠️ 关于 GitHub 分发：如实说明两件事

本地源头现在**本来就是一个 git 仓库**（单仓，D11），公开仓库仍然**是一份压平的快照**——
文件全在，那份 git 历史不随分发。两个后果：

1. **`scripts/init-repos.sh` 仍然要跑。** 用 GitHub 的 **zip 下载**拿到的那份连 `.git` 都没有，
   没有 `.git` 就没有 `core.hooksPath`，没有它提交硬闸**静默失效**——不报错，只是那套纪律悄悄不存在了。
   （`git clone` 拿到的已经有 `.git`，脚本只会补验一次 hooksPath 就跳过。）
2. **「一条日志 = 一次提交」这个对应关系，在分发的这一份里对不上号。**
   跑完脚本整棵树只有 1 次提交，而 7 个单元的 `CHANGE-LOG.md` 里各躺着一整串历史记录
   （少的 9 条，多的二十几条）——
   那些记录属于源头的历史，随文件过来了，随历史没过来。
   🔴 **这个不变量在你自己新建的项目里从第一天起就成立**：清空示例记录 → 写第一条真实记录 →
   第一次提交，从那以后 `git log --oneline | wc -l` 与
   `grep -cE '^\| [0-9]{4}-' CHANGE-LOG.md` 就该永远相等。

**在源头这一份里，这个不变量是按单元逐个可验证的**（两个数字必须相等）：

```bash
git rev-list --no-merges --count HEAD -- <单元路径> ":(exclude)<单元路径>/projects"
grep -cE '^\| [0-9]{4}-' <单元路径>/CHANGE-LOG.md
```

（仓库根这个单元把路径换成 `.` 和 `":(exclude)projects"`。merge 提交豁免——
单仓迁移接历史时产生的 6 个 merge 不代表任何单元的一次改动。）

🔴 **公开仓库永远是快照，源头的 git 历史永不直接推上去。**
理由不是懒：那段历史里有脱敏之前的内容与真实提交身份，而出口安检只扫工作区、**不扫 git 历史**。
规矩全文见 [`docs/03-发布与同步.md`](docs/03-发布与同步.md) §1，来龙去脉见
[`docs/02-设计决策.md`](docs/02-设计决策.md) L11。

细节见 [`docs/01-使用指南.md`](docs/01-使用指南.md) §0，取舍见
[`docs/02-设计决策.md`](docs/02-设计决策.md) D10 / D11。

## 想维护这个模板

| 你想干什么 | 去哪 |
|---|---|
| 改规矩 / 改钩子 | 在这里改，**然后同步改模具**。单仓之后两边同处一个仓库，可以**放进同一次提交原子完成**（记得两个单元各记各的日志行） |
| 踩到坑 / 想推翻某个设计 | 一律写进 [`docs/02-设计决策.md`](docs/02-设计决策.md)。**踩了坑不写下来，下一个人还会照着踩** |
| 把改动发布到公开仓库 | 按 [`docs/03-发布与同步.md`](docs/03-发布与同步.md) 走（含出口安检黑名单 + 🔴 历史不出境的铁律） |

🔴 **不同步的规范比没有规范更坏**——agent 会照着规范去找不存在的文件。
本体系的钩子和规矩在树上仍有 **7 份拷贝**（模具与每个 demo 各自出厂自带一套——
那是它们要教给真实项目的形态，不能省），
所以改一条口径时**先 `grep` 全仓库**找出所有提到它的地方，一处改处处改（教训见 `02` 的 L8）。
